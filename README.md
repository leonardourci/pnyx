# Pnyx

Pnyx is the app, a **Hydra** holds its tasks, and search is the **Oracle**. Everything else uses its plain name.

Pnyx tracks explicit tasks in Hydras, each an orchestrator and its tasks. Create tasks and columns inline, attach an interactive agent session, and continue its conversation from the card. Ad-hoc agent sessions stay in History without creating tasks.

A deterministic view of every agent and its work, with an [AXI](https://axi.md/) CLI named `pnyx-axi`.

Pnyx records tasks, attaches one agent session to each task, and queues your replies to that session. It is a view over the tools you already use, not an orchestrator: Claude Code and Codex hooks report sessions, a Firstmate integration reads Firstmate's own records, and linked pull requests come from GitHub. Every change is an event in an append-only log, so the Hydra can be replayed and audited. Pre-v1.

![Pnyx demo](docs/media/demo.gif)

The demo uses a synthetic fixture Hydra. It shows `pnyx-axi setup hooks`, `pnyx-axi serve --home`, a Hydra and its columns, a card opened on its conversation, a card moved with `m`, a history search with `/`, and `pnyx-axi stop` plus `pnyx-axi setup hooks --remove`.

## Install

Needs Node 22.13 or newer and pnpm (the version pinned in `package.json`).

```sh
git clone https://github.com/leonardourci/pnyx.git
cd pnyx
pnpm install
pnpm run build
pnpm add -g "$PWD"
pnyx-axi --version
pnyx-axi setup skills
```

`pnpm add -g` links the clone, so after a `git pull` you only rerun `pnpm install && pnpm run build`. `pnpm link --global` does not work with this pnpm; use `pnpm add -g "$PWD"` (or `npm install -g .`). Without a global install, run `./dist/cli/pnyx-axi.js` from the clone.

`pnyx-axi setup skills` installs `pnyx-hydra` and `pnyx-worker` once as links into `~/.claude/skills/` (or `$CLAUDE_CONFIG_DIR/skills/`) and `~/.agents/skills/`. Workers in any project or copy can load the worker skill and report to their card. The links point to this installation, so skill updates apply without copying them into projects. Keep the installation in place; rerun setup if a link is missing. Existing files and unrelated links are preserved; move a conflicting skill aside before installing. Use `pnyx-axi setup skills --preview` to inspect the links and `pnyx-axi setup skills --remove` to remove only this installation's links. Check readiness with `pnyx-axi integrations` or Settings > Integrations.

User data lives in `~/.pnyx` by default. Set `PNYX_HOME` to keep it anywhere else; the clone holds only code.

## Projects

A Hydra can work across several projects. Each project is a folder on your laptop, shown by its folder name. Attach an existing folder or clone code into a destination you choose:

```sh
pnyx-axi project add /path/to/project --hydra work
pnyx-axi project add --clone https://example.com/team/project.git --into /path/to/new-project --hydra work
pnyx-axi project list --hydra work
pnyx-axi task create --title "Ship the change" --project project --hydra work
pnyx-axi task project <task> --project project --hydra work
pnyx-axi project set project --copy '<shell command>' --hydra work
pnyx-axi project remove project --hydra work
```

Clone runs ordinary git directly, without sending the URL to an agent. `--into` is required. Relative paths are resolved from the CLI's working folder; in the UI, type an absolute laptop path or start with `~/`. Removing a project only detaches it: tasks, history and the project record stay. Add its path again, or choose Re-attach under Settings → Projects → Detached, to bring it back. Use a full path when folder names are ambiguous.

An empty Hydra offers **＋ Add a folder** and **⎘ Clone a repo** where its chat will appear; the box folds away after the first project. Add a folder completes typed paths from disk and offers one-click folders recorded in agent History. Clone a repo shows the selected destination’s name and path and previews exactly where the code will land: an empty folder is used directly, while a populated parent gets a new folder named after the repository. Cloning runs locally through `project add --clone`. A folder already attached to other Hydras names every one in an inline confirmation; **Add anyway** attaches it, and each Hydra link opens in a new tab. Workers normally get their own copies; only one Hydra at a time may have a worker editing the shared folder itself.

Settings → Projects saves each project’s start command with a name and a **Brings its own folder** switch. Check it when the command creates the worker’s folder itself. Hydra’s summary, `project list` and light check include these settings. Save them from the CLI with `pnyx-axi project set <project> --command-name "Local worker" --command '<shell command>' --brings-own-folder true --hydra <id>`; an empty `--command` clears the setting. Hydra assigns the task’s project, then selects that command with `pnyx-axi task start <task> --via command --command "Local worker" --hydra <id>`. It uses the same task environment as the Hydra’s command. Pnyx normally starts it in the task’s own project copy; checking **Brings its own folder** skips that copy and runs the command from the project folder. Hydra can choose `--folder` or `--in-place` explicitly.

Workers start in their task's own copy of its project by default: on the first start Pnyx makes a git worktree of the project on branch `pnyx/<hydra>-<task>`, kept under the Hydra's folder (`hydras/<hydra>/copies/`), and later starts of that task reuse it. `task start --in-place` works in the project folder itself instead; it is refused while a worker of another Hydra runs in that folder. A project can make its copies its own way: `pnyx-axi project set <name> --copy '<shell command>' --hydra work` runs that command in the project folder with `PNYX_TASK`, `PNYX_TASK_TITLE` and `PNYX_PROJECT` in its environment, and it prints the new folder's path last; an empty `--copy` goes back to git worktrees. A Hydra start command that makes its own folder skips the copy with `hydra set --command-folder own`.

When a task reaches Done and its agent is no longer working, Pnyx removes its copy if it has no uncommitted changes and its work has landed: its commit is on the default branch, or its linked pull request merged. The branch always stays, and a copy whose commit is on no branch is never removed this way. Files git ignores go with the copy. A copy made by the project's copy command is only released: its folder stays for that command's own tool. Otherwise nothing is committed or removed; the task keeps its copy, flagged, and Hydra gets a message to resolve it. `pnyx-axi task copy <task>` shows the copy and that check, and `task copy <task> remove` checks again once the work has landed. Hydra confirms a clean copy whose work already landed another way, or is empty, with `--safe`; discarding work that never landed takes `--discard` with the owner's `--confirm <token>`, never Hydra's. On a Firstmate-linked Hydra, Firstmate makes and cleans its own copies.

Sharing a folder between Hydras requires an explicit confirmation naming the other Hydras. The CLI returns a token; repeat the attachment with `--confirm <token>`. Settings shows a confirmation dialog with links to those Hydras. Hydra's summary and light check include its projects. On a Firstmate-linked Hydra, the home’s project folders appear read-only and are managed by Firstmate.

## Run

```sh
pnyx-axi serve
```

One server runs every Hydra in the Pnyx data folder (`~/.pnyx`, or `PNYX_HOME`): one port, each Hydra at its own path, http://127.0.0.1:4747/hydra/<id>/, with http://127.0.0.1:4747 opening the default Hydra. Open the `url` it prints; `--port` picks another port, and if that port is taken, `serve` exits with `PORT_IN_USE` rather than picking another. The Hydras list in the left panel switches between Hydras on the same server, and a Hydra created while the server runs is served as soon as its folder appears. A Hydra that fails to load is skipped and reported (in the `serve` output and at `/health`), and the others keep working. Each Hydra keeps its own hook socket, its linked Firstmate home and the agents Pnyx started for it, all inside that one process. `pnyx-axi` with no arguments shows the Hydra summary and the running server's address. Stop a foreground server with Ctrl+C or `pnyx-axi stop`, which stops the server of every Hydra. The login service uses the Node executable and Pnyx installation that ran setup, reaching Node through a link on `PATH` such as `/opt/homebrew/bin/node` when one points to it, so a Homebrew upgrade keeps the service starting; keep that installation in place and rerun setup after moving it or switching Node. Rerunning setup on a running service replaces it in place: it waits for launchd to finish stopping the old job before starting the new one. Each Hydra permits one server even when two starts race. A service-managed server restarts after `stop`; use `setup service --remove` to keep it stopped.

The browser reconnects automatically with capped backoff and a heartbeat, resumes Hydra events and restores the open conversation subscription. Composers stay usable during an outage; submitting a message keeps its draft and sends it when the connection returns, using the same delivery key on retries. A failed send leaves one short line in the conversation. The pnyx name in the left panel shows an offline mark when the server cannot be reached. Session identities and attachments live in the event log and survive browser reloads and server restarts.

When the server restarts on a new build at the same port, an open Hydra reloads itself and keeps the open card, unsent drafts and scroll position.

To keep it running in the background:

```sh
mkdir -p ~/.pnyx
pnyx-axi setup service                     # macOS: start now and at login, restart after exit
pnyx-axi setup service --port 4748         # on another port
pnyx-axi setup service --preview           # inspect the launchd configuration
pnyx-axi setup service --remove            # stop and uninstall the service
```

There is one login service for every Hydra. Setting it up replaces the one-per-Hydra services older versions installed for the same data folder.

## Add your agents

```sh
pnyx-axi setup hooks                    # Claude Code and Codex, whichever config folder exists
pnyx-axi setup hooks --harness codex    # just one
pnyx-axi setup hooks --preview          # show what would change
pnyx-axi setup hooks --remove           # take Pnyx's hooks out again
```

This adds a silent reporting hook to `~/.claude/settings.json` and `~/.codex/hooks.json` (`CLAUDE_CONFIG_DIR` and `CODEX_HOME` are honored), keeping every other hook. Hooks record sessions for explicit attachment and watch one thing in each, as Paseo does: whether the agent is working on a turn (from a prompt or tool call) or finished it (Claude Code's and Codex's Stop hook), shown as a small indicator on the card. Ad-hoc sessions never create tasks; sessions without an interactive terminal stay in History. Each interactive session records the terminal it runs in so the Hydra can type your replies into it: a tmux pane, a Herdr pane, a Paseo terminal, or an iTerm2 or Terminal window (macOS asks once to let Pnyx control that app; the answer lives under System Settings > Privacy & Security > Automation). A task without a reply route keeps its draft; failed sends show a short line in the conversation. Already had the hooks installed? Re-run `pnyx-axi setup hooks` to enable typing into sessions. Codex asks you to review and trust new hooks once: run `/hooks` in Codex after installing. Rerun `pnyx-axi setup hooks` after upgrading Pnyx so the hooks cover the events the new version reads.

## Firstmate

Each Firstmate home gets its own Hydra. `pnyx-axi hydra homes` lists the homes beside each other, as `new-firstmate` makes them (in `FIRSTMATE_FACTORY_BASE`, by default `~/projects/agentic-engineering-workflow`; `--base` picks another folder), and the Hydra each one has; `pnyx-axi hydra create --firstmate <home>` creates a Hydra named after the home. `pnyx-axi setup hydra --home <home> --hydra <id>` makes the home that Hydra: it copies the `pnyx-hydra` skill into the home's `.agents/skills/` as a local skill (listed in the clone's `.git/info/exclude`, so Firstmate's tracked files never change) and leaves Firstmate an inbox note pointing at it. A Hydra run by a Firstmate home watches that home when served, without `--home`.

`serve --hydra <id> --home <home>` uses a home that Hydra has not recorded; a Hydra mirrors one Firstmate home, and `serve`, `firstmate sync` and `firstmate watch` name any other home they ignore. The server watches the home's `state/` and `data/` folders, turns each task into a card, and sends your replies through the home's own `bin/fm-send.sh`. Apart from `setup hydra` adding its local skill, it only reads the home. Without a server, `pnyx-axi firstmate sync --home <path>` folds a home in once and `pnyx-axi firstmate watch --home <path>` keeps doing so; `pnyx-axi reply <id> --text <text> --home <path>` replies from the terminal. The first interactive Claude Code or Codex session in an open task's worktree joins that task; a later session in the same folder stays unassigned. The managed task keeps replying through Firstmate. A setting change from a task card's Agent tab goes to the orchestrator as a request note through the home's `bin/fm-inbox.sh note --request-id <id>`, with the same request id retained on retries. When Firstmate records a Paseo terminal, only sessions in that terminal can join or replace its worker; a replacement on the same terminal continues the task while earlier sessions remain in History.

## Task records

Hydra can be Firstmate or an ordinary agent session. Each Hydra has one orchestrator identity, and each explicit task has zero or one attached worker. Tasks support one level of subtasks. Pnyx records work and queues messages; Hydra decides what to do and dispatches workers. Changing Hydra preserves tasks, earlier worker attachments and messages to previous Hydras.

Use `hydra create|set|show|list` for Hydras, `column create|rename|describe|resize|delete|reorder|list` for their columns, and `task create|brief|hide|unhide|hide-after|rename|status|list|show|history|chat` for work records. `task create --parent <task>` creates a subtask. Creating a task in a role column records that role's initial status. The owner arranges cards, and Hydra may place one in response to its own agent doing something that calls for it, guided by the column descriptions. A status declaration alone never moves a card; `move <task> <column> [--before <task>]` (or dragging the card) sets both. `column delete <id> --to <column>` moves every task in the deleted column to `--to` (the first remaining column by default), and Undo refuses to overwrite later edits. The final column cannot be deleted. CLI card moves, column reorders and column deletes first return `confirmation: needed` with a token and a summary; repeat the exact command with `--confirm <token>` to act. A changed target invalidates the token. Browser gestures act directly on the owner’s instruction. Hydra’s own changes (writes with actor `hydra`) through `move`, `task create|brief|hide|unhide` and `task start` must carry one short `--reason "<why>"`. Pnyx stores it on the event, shows it in the task’s history and posts one line in Hydra’s chat built from the action and the reason, such as “Moved API cleanup to Needs you: its agent asked which schema to use”; the command returns that line as `posted`. An optional `--details "<more context>"` appears under the line. The owner’s own moves and edits need no reason.

Create a task with `task create --title "<title>" --brief "<instructions>"` and edit its brief with `task brief <task> --brief "<instructions>"` (empty text clears it). Starts include the brief in the opening prompt, whether Pnyx runs the agent or it starts through Paseo, Firstmate or the configured command. An explicit `task attach` sends it through the attached agent’s reply route once per attachment; the attachment receipt includes its delivery result. `task hide <task>` removes work from the live Hydra and `task unhide <task>` restores it; both are events and preserve all history.

Set a reminder by telling Hydra “remind me about this tomorrow” or using a card’s ⋯ → Remind me…. The CLI is `pnyx-axi task remind <task> "tomorrow 9:00" --hydra <id>`; it also accepts `"in 2 hours"` or a future ISO timestamp with a timezone. “Tomorrow” uses the laptop’s timezone and defaults to 9:00. Each task has one reminder: setting another replaces it, and `task remind <task> clear` clears it. Waiting reminders appear on cards; `task reminders` returns their list and count, also available at `/hydra/<id>/reminders` for the panel. When a reminder falls due, the server records one event, moves the card to Needs you (restoring that column if it was deleted), brings a hidden card back, and posts a reminder in Hydra’s chat. Hydra’s light check includes the due event. Missed reminders fire when the server next starts; no agent is started and nothing is deleted. On a Firstmate-linked Hydra, an unchanged record leaves a due reminder in Needs you; clearing the reminder or new Firstmate records resumes source placement.

Columns carry a description of what belongs in them, available through `column list` and set with `column create --description "<when and why>"` or `column describe <id> --description "<when and why>"`. `column resize <id> --width <pixels>` and `hydra resize --width <pixels>` persist widths. `layout show` reports overrides and stored defaults (290 pixels per column, 360 for Hydra); `layout reset` restores those widths while preserving other preferences.

Hydra’s memory is available through `hydra memory list`, `hydra memory set --key <short-name> --text "<fact and why>"` and `hydra memory forget --key <short-name>`. Entries replace by key, survive a Hydra switch and remain isolated to their Hydra; all replacements and removals stay in the event log. Hydra reads memory at startup and stows concise lasting facts before a context reset.

A task's status is an explicit declaration (working, needs_you, paused, blocked or done) shown on its card; neither a declaration nor a merged pull request moves the card. Silence, finished turns and session exit do not complete tasks. Firstmate's backlog, status text and worker metadata are mirrored into retained task records, including backlog items without workers. A Hydra stops mirroring a home when that home no longer runs it.

The append-only log preserves Hydra, task, subtask, session, command and message identities. Replaying existing events migrates old session records without changing their event bytes or ids. Unattached and headless sessions remain available in History and search. Harvested user and assistant messages are redacted and copied into the log on turn end, attachment changes and explicit `harvest`, so observed conversations remain readable and searchable after a native transcript disappears. Oracle remains a derived, deletable index.

`hydra send --text <message>` queues a Hydra-level message with no task. `hydra send --task <task> [--action send|worker]` queues a task-specific message, and `hydra messages` reads the queue. These actions never launch a worker; starting one is `task start` (below). Hydra’s own messages (actor `hydra`), including the lines Pnyx posts for its changes, appear in the chat as Hydra’s and stay readable through `hydra messages`, task history and `hydra check`, which lists them without waking on them. Several workers per task, automatically generated labels and quota reporting are later work.

## Starting workers and Hydra

`pnyx-axi task start <task> --via pnyx|paseo|firstmate|command` starts one worker for a task and attaches it; `pnyx-axi hydra start --via paseo|firstmate|command` starts the Hydra. Pnyx runs the agents it is asked to start; Hydra still decides what to do. Pnyx records each start on the Hydra.

- **Pnyx (the default):** `task start <task> [--kind <kind>] [--harness claude|codex] [--prompt "..."] [--folder <path>]` has the Hydra’s server (`pnyx-axi serve`) run Claude Code through the Agent SDK or Codex through `codex app-server` in the task's folder, with the brief as its first prompt. It records the native session or thread id, folder and settings on the task and loads your own provider configuration, skills and hooks. Install the chosen provider's CLI and sign in before starting. Hooks report to the same task. The chip reads **Claude Code · Pnyx** or **Codex · Pnyx**; the composer, `pnyx-axi reply` and model, effort and mode pickers (`pnyx-axi agent`) go straight to it, and working or finished comes from the agent itself. Codex applies picker changes on its next turn and queues messages sent during a turn. Stopping the server stops its agents: after a restart each task still shows its agent and conversation from the provider's own history, a running turn is marked interrupted and waits for you or Hydra, and the next message resumes the same session or thread. Tool permission requests appear inline with **Allow / Deny** and a **Needs you · permission** marker; the card stays in its column. Hydra sees them through `hydra check` and can answer with `pnyx-axi task permission <task> <request> allow|deny --actor hydra --reason "<why>"`; its reason appears in Hydra’s chat. Your own permission rules run first, so tools they already allow never ask in the Hydra. The first answer wins and does not change your permission rules. Command and file approvals apply once; Codex turn-permission requests show their turn scope and never grant session-wide access. Requests the agent no longer waits for expire, including after a server restart. Codex's mode selects its approval policy (`untrusted`, `on-request` or `never`); its sandbox follows your Codex configuration.
- **Paseo:** with [Paseo](https://paseo.sh) running, `--via paseo [--kind <kind>] [--harness claude|codex] [--prompt "..."] --folder <path>` asks the local daemon (`PNYX_PASEO_URL`, default `ws://127.0.0.1:6767/ws`) to start a Claude Code or Codex agent; the conversation and replies then go through Paseo, and the agent stays in Paseo too. Pnyx says so when Paseo is not running and never starts it. `task paseo` checks the daemon.
- **Firstmate:** on a Hydra run by a Firstmate home (the default route there), `--via firstmate [--prompt "..."]` puts a worker request in Hydra's chat and hands it to Firstmate as an inbox note. Firstmate dispatches the worker; its mirrored task can be nested under the Hydra task.
- **Your own command:** `pnyx-axi hydra set --hydra <id> --command '<shell command>'` sets a command, run in the task's folder with `PNYX_HOME`, `PNYX_HYDRA`, `PNYX_TASK`, `PNYX_ROLE` (`worker` or `hydra`), `PNYX_TASK_TITLE`, `PNYX_PROMPT`, `PNYX_HARNESS` and `PNYX_FOLDER` in its environment. The session it starts attaches to its task, or becomes Hydra, when its hooks first report.

Every agent Pnyx starts carries `PNYX_HOME` and `PNYX_HYDRA`, so its hooks report to the Hydra that started it, even from a separate Pnyx home, once `pnyx-axi setup hooks` has installed this version's hook. `pnyx-axi integrations` shows which of global skills, hooks, Paseo, Firstmate, the configured command and GitHub are ready, with the command that sets each up; the same list is under Settings > Integrations.

### Kinds, the light check and the worker contract

```sh
pnyx-axi kind set default --harness claude --model claude-opus-5-5 --effort high --mode acceptEdits
pnyx-axi kind set review --harness codex --effort high --quota high
pnyx-axi kind set hydra --harness claude --model claude-sonnet-5-5
pnyx-axi task start <task> --kind review
pnyx-axi hydra check --after <seq> --wait 1800
```

- **Kinds:** `kind set` records the agent each kind of task starts on: harness, model, effort and mode. Agents that Pnyx runs take their own model and effort; mode is Claude Code’s permission mode (such as `acceptEdits` or `bypassPermissions`) or Codex’s approval policy (`untrusted`, `on-request` or `never`); in Paseo, effort is Paseo's thinking option and mode is Paseo's mode. `--quota high|medium|low` picks, at start, the model with the most runway in that intelligence bucket for the harness through `quota-axi`, falling back to `--model` or Paseo's default. `task start` uses `--kind` or the `default` kind, and `hydra start` the `hydra` kind; without one, Claude Code with its default model. `--harness` on a start overrides the kind's; switching providers uses the chosen provider's model, effort and mode defaults and resolves quota for that provider, and without `--prompt` a worker opens with a message naming its task and the `pnyx-worker` skill. Set a flag to an empty value, or `--quota off`, to clear it. `--fast on|off|default` saves Fast for an external agent’s next start; `default` restores the harness default. Settings → Agents on the Hydra edits the same kinds, and each change is its own event in the log; saving a kind never chooses the Hydra.
- **Direct conversations:** every owner message sent through a task card is already recorded with its send receipt. The light check also archives native transcript messages and completed Paseo replies into the same event log, including chats retained after detach and messages from an earlier task attachment. It returns a compact `conversations` digest grouped by task; Hydra treats the owner’s direct words as instructions and decides whether to act or take note. Excerpts point back to full task history, and the `through` cursor pages every event without dropping the rest. Echoes of Hydra sends and Hydra’s own answers are excluded from the digest. Unavailable native sources are reported for a later retry. Workers can escalate directly with `hydra send --task <task> --text "<question and context>"`.
- **Light check:** `hydra check` also returns an `agents` list with each attachment’s session, harness, launch route, folder, start time, last observation and current presence. A terminal observed before this boot or a process that exited is `gone`; a daemon or process that cannot be queried is `unknown`. These are observations for Hydra to inspect with `task history` and `task show --full`; Pnyx never relaunches agents. `hydra check` prints only what Hydra tracks (messages, task creation, brief and visibility changes, declarations, open agent questions, attachments, column changes, manual moves and links) after `--after`, with each event's id, task and message action, and skips Hydra's own writes (actor `hydra`, from `PNYX_ACTOR` or `--actor`). With `--wait` it blocks until one appears, so a background command or monitor wakes Hydra only when something changed, without loading the Hydra.
- **Workers:** a worker follows the `pnyx-worker` skill and reports with `task status <task> working|needs_you|paused|blocked|done --note <text>`; silence, idling and exit change nothing. Run `pnyx-axi setup skills` once to make both skills available globally in any project or copy.
- **Binding a session yourself:** `hydra set --session self` and `task attach <task> --session self` pick the session running in the caller's own Paseo terminal, tmux pane or Herdr pane.


## Using Pnyx

Create a task inline in any column with **+ Add task**, enter its title and initial prompt, then save. Saving opens the card and focuses its composer without launching an agent. **+ Add column** creates a column and focuses its placeholder title. Creating a task clears active filters so the title stays visible. Rename a task in place, double-click a column title to rename it, and drag cards or column headers to move them; a card dropped on another goes above or below it by where it lands. Column deletion asks for inline confirmation and offers Undo.

- **Hydras:** the left panel lists every Hydra and expands to its projects, with live workers and waiting asks per project. Click a project to filter its cards; click again to show all cards. Click a Hydra name to open its page on the same server, or double-click the current name to rename it. **＋** beside Hydras opens a name field; Enter creates an empty Hydra and opens it. **＋ Add project** opens the folder and clone actions beside the columns.
- **Card states:** cards show their project, title and whether work has not started, is working, finished its turn, stopped, asks or is done. Stopped workers show a red square and their stop time; Resume on hover asks Hydra to continue them. A copy that needs attention says “copy not cleaned”. Card and column ⋯ menus include Copy ID. Newly created cards and columns use a kind and a random UUID; existing IDs remain valid.
- **Columns:** every Hydra starts with Queued, In progress, Needs you, Parked and Done. A task created without a column starts in Queued. A Hydra from an earlier version moves onto these columns on its next write, placing each card from a column that goes away by its status, and keeps the columns you added. Use `pnyx-axi column create|rename|reorder|delete` to edit columns. Cards stay in the order you put them; agent state, declarations and merges never move or reorder one. Silence, finished turns and session exit never complete a task.
- **Firstmate Hydras:** the five default columns are always present. You can rename, describe and reorder them and add your own, but deleting one is refused in place with “Can't delete: this column is tied to Firstmate's records”. Cards move between them by each column's role, whatever its title, from Firstmate's records, with Firstmate's latest status line as the reason: a queued item goes to Queued, work in flight to In progress, an open decision, a failed or blocked latest line or a captain hold waiting on you to Needs you, a dated, aged, blocked or other hold to Parked, and a closed item to Done. A card you drag into a column of your own stays there until its Firstmate record changes.
- **Task conversations:** cards stay 176 px closed and 480 px open, capped by the column pane on short screens. The title, project label, activity and composer stay anchored while the conversation scrolls inside. The latest worker declaration appears at rest; opening the card shows its initial prompt, factual update history and messages in one stream. User messages align right, agent updates left. Task declarations also appear in Hydra’s chat with the same task reference. A finished turn never marks a task Done.
- **Tasks and agents:** only Hydra attaches or reassigns an agent. **Start**, **Resume** and **Reassign** send task-scoped requests to Hydra; Firstmate-linked Hydras send them to Firstmate’s inbox. The existing attachment stays until Hydra changes it. Hydra and scripts can use `task create --title "Work to do" --brief "Initial prompt"`, `task sessions`, `task attach <task> --session <session>` and `task detach <task>`. Attaching or detaching never starts or stops a process. Hydra can continue an ended outside Claude Code or Codex session with `task continue <task>` after checking its recorded process has exited; `task continue <task> --check` only reads eligibility. A fresh start uses `task start <task> --via pnyx --replace-session <session> --folder <path>` and preserves the attachment when validation fails.
- **Task delivery:** every card message is saved in Hydra’s durable queue with its task reference and sent through the attached worker’s route. Without an agent, it addresses Hydra and stays in task history for assignment. Agent delivery and Hydra queue acceptance have separate receipts; Firstmate Hydras also report the inbox delivery. Queued means available for Hydra to read, not handled. Failed or uncertain routes keep the draft. Retrying the same attempt never resends a confirmed or uncertain worker delivery, and never duplicates the Hydra message. The CLI equivalent is `pnyx-axi reply <task> --text "Context" --task-message --idempotency-key <key>`. Ordinary `reply` remains a direct worker send.

- **Agent questions:** when a session in a tmux pane waits on its own question, permission, plan or MCP form prompt, the task's conversation (or Hydra's chat, for Hydra's session) shows it with the options its terminal shows; answering types the keys that prompt expects. It shows as answered until the session's hooks report it moved on. Other terminals are answered in the session itself.
- **Hydra:** its chat stays docked on the left, with its composer at the bottom. Mod+Enter sends and Enter adds a line. Mod+B hides the left panel completely and brings it back. The single agent picker stages the provider, model, mode, effort and supported Fast settings until Apply; these save for Hydra’s next start and never start or attach an agent. A Firstmate-linked Hydra has no picker for Hydra itself because Firstmate owns its agent. Reminders shows the waiting count for the current Hydra and opens its list in place, soonest first; click one to open its card.
- **Columns:** drag a header to reorder columns, or focus a header and use Mod+Left/Right. The ＋ creates a task at the top. The ⋯ menu copies its ID, renames, edits the hover description or deletes the column with an inline Yes/No confirmation; on a Firstmate Hydra, Delete on a default column shows why it is refused instead. Drag the invisible right edge of a column or Hydra to resize it; Settings resets widths to their defaults.
- **Cards:** show their title and whether the attached agent is working, finished its turn or stopped (its session ended), so a dead worker never looks active. Settings can add the last message. Click a card or press Enter to expand its conversation downward at the same width. A task without a conversation opens to an editable brief; a worker started for it receives that brief as its opening prompt. Its ⋯ menu contains agent attachment and Add subtask. Summary and decision notes stay in the task record for Hydra.
- **Conversations:** replies use Markdown, user messages appear on the right, and tool calls and thinking use one-line rows. Select text with the mouse or keyboard caret, or press `c` on a block, to add independent comments, including nested passages. Comments travel with the next reply, identifying its original message time and including the paragraph for a selection of three words or fewer. The first comment in each conversation adds a short internal explanation marked “no reply needed.” Settings has separate Focus mode, Tool call details and Thinking details toggles: Focus hides traces; the details toggles decide whether visible rows expand.
- **Composer:** starts with a 36 px draft and a 32 px control row, grows the draft to 128 px and then scrolls it. Drag its top edge to resize, capped at about 35% of the pane. The ＋ menu inserts UTF-8 text files within the 64 KiB total message limit (including the draft, comments and transport encoding) into the draft or inserts @ at the caret for task mentions. File contents go with the message only when it is sent.
- **Agent settings:** one composer picker groups the attached agent, model, mode, effort and supported Fast controls from the integration. Selecting an option stages it; Apply sends the changes through the agent's own route, or asks Firstmate for a task worker's change, and they remain pending until reported. The compact summary shows reported settings and pending confirmation; configuring a session does not attach or reassign it. Direct Codex model and approval changes still use its native pickers; those unsupported controls stay disabled in Pnyx. `pnyx-axi agent <id>` provides the same integration controls.
- **Keyboard:** Mod is Command on macOS and Control elsewhere. Every binding can be changed in Settings, and the Character shortcuts switch there turns off the single-key ones.
  - Arrows or h/j/k/l: move between cards and columns; Home/End: first or last card
  - Enter: open the card's conversation at its reply input; `r`: focus the reply input; Mod+Enter: send (plain Enter adds a newline)
  - In the conversation: Escape from the reply input, Up at the very start of its draft, or Mod+L puts a text caret in the latest reply. Arrows, word and line jumps, Home/End and Page Up/Down move it like a text editor, skipping tool calls and thinking, and Shift extends a selection; with a selection Enter comments on it, typing starts a comment and Shift+Enter quotes it into the reply. `c` comments on the block at the caret, j/k jump between blocks, Down past the end or Mod+L returns to the reply input, Enter without a selection does too, and Escape hides the caret. Typing never changes the messages. The caret needs a Chromium browser.
  - Escape: dismiss suggestions, leave the reply input for the caret, hide the caret, then close the card
  - Mod+arrows: move the highlighted card or column; `/`: search history; Mod+F: focus Oracle
  - Mod+K: reveal the panel and focus Oracle; Mod+,: Settings; `?`: keyboard shortcuts in Settings
- **Oracle:** the left-panel Oracle field, History and `pnyx-axi oracle "<words>"` find cards by meaning, in any language, as well as by their words, across titles, links, events, notes and transcripts. Semantic search runs local models on your machine; the first search downloads them in the background (about 1 GB with a GPU, 115 MB on CPU only), and searches are full-text until they are ready. `pnyx-axi oracle status` shows the progress. The panel field filters tasks in place and lists matching task conversations and Hydra’s chat in a floating list directly beneath it, without dimming or moving the page. Escape closes the list and clears the filter. Settings change directly in their result rows, and layout actions are available there too; start a query with `>` to show only settings and actions. Hidden sessions stay in History, reached through the “Search history” row. ⌘K (Ctrl+K elsewhere) focuses the same field, including from a reply composer and when the panel is hidden.

Run `pnyx-axi --help` for every command.

## Skip semantic search

On a slow laptop, or to keep search full-text only:

- Leave out the optional packages it runs on (node-llama-cpp and sqlite-vec): after `pnpm run build`, run `pnpm install --no-optional` in the clone (before the build it would also drop the build tools' own native parts). Oracle then falls back to full-text silently.
- Or switch it off: Settings → Oracle, or `pnyx-axi settings set oracle.semantic off`. `PNYX_SEMANTIC=off` does the same for one shell or script. To free the disk, delete `~/.pnyx/models/`.

`pnyx-axi settings set oracle.rerank off` keeps meaning but skips the reranker, which costs about 0.4 s a search on a GPU (`auto`, the default, turns it off on CPU-only machines).

## Where data lives

Everything is in `~/.pnyx/` (or `$PNYX_HOME`): the hook script in `hooks/`, the local write token, `settings.json`, the semantic search models in `models/` with the worker's `semantic.log`, and one folder per Hydra in `hydras/<hydra>/` with `events.jsonl` (the append-only log), `snapshot.json`, `search.db`, `harvest.json` and `copies/`, the task copies Pnyx made. Hydras from an older version move from `boards/<hydra>/` to `hydras/<hydra>/` on the first run, without overwriting or deleting anything: a Hydra that an older server still runs moves after that server stops, hook events spooled on either side are kept, a Hydra with task copies leaves a `boards/<hydra>` link to its new folder so the agents and git repositories using those copies keep their paths, and a Hydra found in both folders stops every command until one of the two is moved away. Existing Hydras keep their `search.db` caches and event vocabulary, saved search settings and service identities. Snapshots from an older version rebuild from the unchanged event log. The CLI uses `hydra`, `--hydra` and `oracle`; old command names and flags have no aliases. Rerun `pnyx-axi setup hooks` and `pnyx-axi setup service` after upgrading so installed hooks use `PNYX_HYDRA` and the `hydras/` folder, and one login service runs every Hydra. Restart agents started before upgrading so their hooks inherit `PNYX_HYDRA`; their recorded tasks and conversations remain in the log. Nothing at runtime writes inside the repository.

To start a Hydra over, stop the server and delete its folder: `pnyx-axi stop && rm -rf ~/.pnyx/hydras/default`. That folder also holds its task copies, so settle them first with `pnyx-axi task copy <task> remove`, and run `git worktree prune` in each project afterwards. `pnyx-axi oracle rebuild` rebuilds only the search index.

## Uninstall

Remove the hooks first, since they point at the script in `~/.pnyx/hooks/`. Deleting `~/.pnyx` also deletes the task copies under each Hydra's folder, so settle them first:

```sh
pnyx-axi stop
pnyx-axi setup hooks --remove
pnyx-axi setup skills --remove
rm -rf ~/.pnyx
pnpm remove -g pnyx-axi
```

## Development

See [AGENTS.md](AGENTS.md) for the layout and design rules. `pnpm run lint` and `pnpm test` give deterministic verification. `pnpm test:web` runs a real browser smoke test through `chrome-devtools-axi` with a temporary `PNYX_HOME`, a random port, synthetic transcripts and a fake Firstmate send script; set `PNYX_EVIDENCE_DIR` to a folder outside the repository to keep its screenshots. `pnpm test:keyboard` exercises navigation, card and column moves, the left panel, comments and independent task/Hydra sends with real browser keys. `pnpm test:chat` covers Markdown rendering, nested comments, their delivery format and the reply input. `pnpm test:connection` covers offline sends, event resync, subscription recovery, reloads and heartbeat recovery. `pnpm test:semantic` checks semantic search on the real models; set `PNYX_GOLDEN_MODELS` to a folder already holding them to skip the download. `pnpm run web:dev` serves the Hydra through Vite.

```sh
pnpm dev
```

`pnpm dev` runs a Pnyx server with its own data folder (`~/.pnyx-dev`, or `PNYX_DEV_HOME`), so it never competes with your installed server for your Hydras, opening its `dev` Hydra under `node --watch`, which restarts it when server code changes, and the Vite dev server, which updates the web app in place as you edit `web/`. Open the URL Vite prints; it forwards the Hydra's WebSocket to the dev server on port 4319 (set `PNYX_DEV_PORT` to change it).

Done cards are hidden from their Hydra after 24 continuous hours in Done. They are never deleted: their tasks, events and conversations stay in History and Oracle. Set the delay for each Hydra in Settings or with `pnyx-axi hydra set --hydra <id> --done-after-hours <hours>`; `0` keeps Done cards visible. Each card’s ⋯ → Hide after menu overrides the Hydra with 1 hour, 24 hours, 3 days, 1 week or Keep visible; Use Hydra setting clears the override. The same setting is available through `pnyx-axi task hide-after <task> <hours|default>` (`0` keeps it visible). Done cards show “done · 2h ago” until their last six hours, then “hidden in 3h”. Other columns never fade. Use the task menu in History to **Bring back to Hydra**, or run `pnyx-axi task unhide <id> --hydra <id>`; a restored card stays visible until it moves out of Done and enters again, or you choose a new hide time. A reopened expired card returns automatically.

Cards show a compact project label beside their short title. Firstmate tasks use the item's project and omit a matching leading `<project>:` from the displayed title. Other tasks accept `pnyx-axi task create --title <title> --project <name>` or `pnyx-axi task rename <id> --project <name>`; an empty project value clears the label. Project labels and task tags receive a curated color on the next write, saved in the event log and reused across the Hydra. Labels use a soft fill and outline and remain searchable in the Hydra and Oracle.

The interface and conversations use bundled GFS Neohellenic; code uses JetBrains Mono. Settings keeps UI, chat and code font-size preferences. Column wells and headings use slate for Queued, blue for In progress, gold for Needs you, violet for Parked and green for Done, with an icon and text identifying each state. Settings → About Pnyx → License notices lists the font and icon licenses.
