# Pnyx

## Names

Pnyx is named after the hill in Athens where the citizens' assembly met to decide.

- **Pnyx**: this app, where every agent and its work is shown.
- **Hydra**: an orchestrator, many heads and one body. Each Hydra has its own columns and tasks, and creating a Hydra creates them.
- **Oracle**: the search field. Search it by keyword; it returns matching tasks, messages, settings and actions, never made-up answers.
- **Polis**: a group of owner and project memory with its own reader list.

Column names are the user's own. Use plain names for the other features.

Run `pnyx-axi` for the Hydra summary and `pnyx-axi --help` for commands. Create tasks with `task create` or `push`. After `setup hooks`, Claude Code and Codex sessions appear in `task sessions`. Attach a session to project its activity and prompts onto a task. `pnyx-axi oracle "<words>"` finds past work across card titles, links, events and notes by keyword, matching word forms, synonyms and near spellings. Results rank by the query words in a card's title, project and link titles, then by its best-matching entry with notes counting double. Saved task briefs, intents, owner asks and investigation reports remain searchable after edits. Read the latest stored report with `task report <task>`. Helper results match their tasks; unchanged helper waits are omitted. `pnyx-axi card <id>` shows a card's summary, decisions and context, harvested from what sessions and linked pull requests already recorded.

When a session waits on its own question, permission or plan prompt, `pnyx-axi card <id>` lists the request with its options and `pnyx-axi reply <id> --answer <request key> --json <answer>` answers it in that session's tmux pane (see `pnyx-axi reply --help`).

When Hydra relays an owner's chat answer to a task question, `pnyx-axi reply <task> --question <question> --from-message <owner-message> --text "<relay>"` records the answer with the outgoing message before delivery. Go/Hold and Merge/Hold questions also take `--choice`. An answered merge Hold can be replaced by `task answer <task> <question> --choice Merge`; an agent answer without a newer owner source produces a notice. Undo restores Hold. Hydra can instead use `task reask <task> <question> --reason "Confirm the merge again"` to restore the review controls on the card; this grants no approval until the owner answers Merge. A plain reply leaves task questions open. A failed delivery can be retried with the same `--idempotency-key` without changing the saved answer.

The owner can send directly with `task send <task> --text "..." --harness claude|codex --event-id <id>`, or create and start with `task create --title "..." --project <repo> --ask "..." --start --harness claude|codex`. This uses the normal task copy and landing rules without a Hydra turn. A send interrupts the current turn before applying harness, model or effort changes. Model and effort changes keep the current session when the harness and account stay the same. A new session receives a command to read the prior conversation. Outside sessions keep their reply route until Continue in Pnyx.

To start a worker for a task, run `pnyx-axi task start <task>`, which has the Pnyx server run Claude Code or Codex using the default dispatch rule unless `--rule` names another rule, with `--harness claude|codex` or `--account <registered name>` to override it, or add `--via command` (see `pnyx-axi task --help`). Hydra follows the `pnyx-orchestrate` skill and the workers it starts follow `pnyx-report-progress`.

`account set <name> --provider claude|codex --folder <path> [--label <display name>]` registers an existing Claude Code or Codex home; Pnyx stores the home, never credentials. A candidate's `account`, or `task start --account <name>`, runs on exactly that login and never on another. Each provider and account pair appears once per rule. The routine helper has its own account, set with `settings set --json '{"helper":{"harness":"claude","account":"claude:work","model":"sonnet"}}'`; leave it alone when changing the main Hydra's selection. See [named accounts and dispatch](../../../docs/pnyx-axi.md).

For related local task changes, prefer one `pnyx-axi apply --file <path|-> --hydra <hydra>` over separate calls. Its versioned JSON document contains `changes` and optional `expected.tasks` revisions; `--check` previews changed fields and collection counts; `--check --full` previews complete records without writing. Supported operations are `task.create`, `task.brief`, `task.owner-ask`, `task.depend`, `task.undepend`, `task.hold`, `task.release`, `link` and `outcome`. `intent` on `task.create` or `task.brief` sets the card's goal; `task.owner-ask` keeps the owner's exact words separately. A create's `as` alias can be used later as `$alias`. Keep the document and `--event-id` unchanged on retries. All changes, including lifecycle effects, commit together; invalid input writes nothing. Correct batches with another apply, since undo refuses their child events. Starts, messages, memory and settings stay separate. See [the operation schema](../../../docs/pnyx-axi.md#atomic-local-changes). Heads dispatch rules and accounts change the same way through `pnyx-axi rule apply --file <path|-> --hydra <hydra>`: the document holds `expected.revision` from `rule show` and a `patch` naming only what changes; `--check` previews it, then the same command without `--check` applies it directly and records a line in chat. Permission increases apply directly with a notice. Legacy `--propose` also applies directly.

`task create --title "<title>" --brief "<instructions>"` files a task and starts its worker; add `--hold`, `--behind`, `--on` or `--no-start` to keep the instructions before an agent exists, and `task brief <task> --brief "<instructions>"` edits them. A start never refuses over an open hold, question, prerequisite or prompt: its receipt lists them under `open` with the command that clears each, and a start on a task with a worker sends `--prompt` to that worker. Starting or explicitly attaching an agent hands it that brief. `task hide <task>` and `task unhide <task>` change visibility while preserving the record. `task move <task> --to-hydra <hydra> --reason "<why>"` moves a task to another Hydra with its record, history and Pnyx-run worker; the task copy stays in place. Moves stop hosted turns, detach outside workers, stop external sources and clear relationships to tasks staying behind. Receipts and affected cards name each adjustment and its corrective command. `undo` points to moving the task back. Task and agent operations record their lifecycle facts; worker.log supplies worker status and the latest line. Column descriptions (`column list`, `column describe <id> --description "<when and why>"`) guide manual moves, reserved for owner requests or exceptional corrections with a reason. CLI card moves and column edits run directly and return their results. `column resize <id> --width <pixels>`, `hydra resize --width <pixels>` and `layout reset [--all]` let Hydra adjust the layout. Settings every Hydra shares (theme, text sizes, cards and chat switches, keyboard bindings, default widths, Hide Done, review cadence, routine helper, whether the Oracle keeps its filters, the Hydra list's order, the diagnostic logs' level, days and size cap) are read with `settings show` and changed with `settings set --json '<patch>'`, naming only the keys that change. `owner memory list|set|forget|move` keeps the owner's preferences and learnings in the Hydra's write polis, and `hydra memory list|set|forget` what only one Hydra needs.

Task moves clear parent relationships crossing Hydras. Keeper moves retain relationships among tasks moving together.

Task copies use readable branches `<hydra-name-slug>/<task-title-slug>`; existing names survive renames and failed allocations keep their reservations. Queued handoffs preserve their source or target assignment across restart according to the committed session event. An unresolved handoff refuses starts, resumes, replies and copy removal with `CONFLICT`; preserve any changed work before requesting a restart, which retries recovery.

A restart or upgrade stops Pnyx-hosted agents; a turn it cut resumes from its saved session when the server is back, and a pending permission request expires, so the agent asks again. Never restart Pnyx to clear a blocked turn. Reconcile unknown answer delivery through its existing receipt.

`pnyx-axi page` summarizes the Hydra as a page shows it; `--full` prints all of it and can be megabytes, so read tasks with `task list` and `card <id>`.

For diagnosis, `pnyx-axi debug timeline --task <task> --hydra <id>` returns bounded identities without conversation bodies; `--message`, `--batch`, `--session` and ISO time filters narrow it. Continue with the returned cursor and the same filters. `debug health` reads current ownership, unsettled inputs, helper completion/deadline facts, spool age and recovery attempts. Unknown means unavailable, not permission to resend or release ownership. Safe failed-message recovery is bounded to two logged attempts using the original idempotency key; inspect its recorded outcome before acting. For slowness, `debug performance` reads the diagnostic logs of the last hour (`--since`, `--until`, `--operation <prefix>`): each action's count, typical and worst duration, errors and warnings, the server's memory over time and the slowest actions. `logs` gives the local JSONL folder and retained sizes. Timed lines include `startedAt`, `at` and `ms`; periodic `process` and `storage` lines include RSS, heap, CPU, loop lag, active resource counts and database/log bytes. Detailed mode adds successful HTTP requests and fast event reads. Logs omit hook payloads and arbitrary error text; error fingerprints, codes and call sites group failures without retaining messages.

For an exact past reply, use `pnyx-axi hydra message --id <message-id> --before 3 --after 3 --hydra <hydra>`, or `task messages <task>` with the same options for a task thread. Select by `--seq <seq>` or `--at <ISO-time-with-timezone>` instead when needed. A selector alone returns one message; `--budget <tokens>` grows its surroundings. `--direction older|newer` pages before or after it, excluding that message, and `--from <seq|ISO-time> --to <seq|ISO-time>` selects an inclusive range. Follow `older` or `newer` with `--cursor <cursor>`; cursors pin the thread, range and snapshot. Pages contain whole messages within the token, count and byte limits. Hydra references stay valid across inscribe, compaction and agent switches; a task's lookup reads its current session and the owner's replies, and `task chat <task> --session <session>` reads a past one. A reference whose transcript is gone returns `NOT_FOUND`. Owner comments include the command for their Hydra and thread; use it, then follow cursors only as far as needed.

Owner questions persist across completed investigations, worker exits and unrelated merges. Use `task discuss-question <task> <question> --text "<clarification>"` to discuss without answering. Short “why?” and “explain” requests are discussion. Longer instructions remain answerable. The owner can choose Later with `task defer-question <task> <question> --until "<future time>"`. Agents can defer directly and receive a notice if there is no owner source. Deferral pauses active attention and reminders, preserves the gate, and ends at the selected time. Ready for review controls share one Merge/Hold approval per PR URL. Task questions stay on their cards. Blockers and tasks the owner selects or mentions also appear in chat. For a decision without a task, use `hydra ask --question "<decision?>" --context "<why, next action and [Hydra](pnyx-task:%24hydra)>" --choice "<recommended choice>" --choice "<alternative>" --recommend 1`. Workers send procedural questions to Hydra with `task ask`. Record a decision already settled by the owner with `hydra send --task <task>`. Automatic question reminders appear together in chat every four hours.

`task questions` lists Waiting on you groups and their shared choices. The owner can use `task answer-group <task> --questions '<JSON array of keys>' --choice '<shared label>' --event-id <attempt>`. Retry an uncertain receipt with the same keys, label and event ID. If delivery reports a changed group, read it again to see which questions still need answers.

`task refresh-links <task>` makes known pull requests due for refresh and looks for pull requests on eligible task branches. Known links are read once per minute while the worker works or checks are pending and every 15 minutes when idle. A failed read keeps that schedule. A link that resolves to no pull request three times waits for a task or link change.

`debug cpu-profile --seconds 10 --out ./idle.cpuprofile --hydra <id>` samples the server's main thread and returns the hottest functions. Only one capture runs at a time; the output file is private, and server shutdown cancels the capture.

Sending an owner message to a busy hosted worker or Hydra interrupts its turn and delivers the message as the next input. Stop a hosted worker with `task stop <task>` or Hydra with `hydra stop`; worker requests proceed with a notice. Stop cancels unread owner inputs and changes only the status, without adding chat text. Bubbles retain the message and send time. Use `hydra cancel <message-id>` to cancel one input held during compaction, upgrade, restart or an agent change. After Stop, routine wakes wait for the owner's next message.

Hide Hydras from the page list and switcher with `settings set --json '{"hiddenHydras":["hydra-2"]}'`. Restore all with `settings set --json '{"hiddenHydras":[]}'`. This shared view setting leaves pages, projects and workers running.

`task merge <task>` checks the task’s merge rule, owner approval, classic protection and reported checks, and binds the request to the verified head. A 403/404 from the branch-rules endpoint means no readable rules there; evidence gaps appear in the receipt and card, and GitHub decides whether the merge can proceed.

### Poleis

The owner can manage polis readers and Hydra home/read lists in Settings, assign project poleis in the project editor, and filter Hydras by polis from the top bar. These controls run the commands below; agent changes apply directly with visibility notices.

Hydra config uses `polis` for its home and `readPoleis` for its read list. The defaults are `shared` and `["shared"]`. Changing the home leaves the read list as-is unless you also pass `--read-poleis`.

`shared` keeps the existing owner memory log. `work` and `personal` start empty with no readers. Reading a polis requires both the Hydra's read list and the polis's reader list to allow it. The server sends owner-memory writes to the Hydra's home polis. Writes outside read scope and above the suggested 24000-character budget proceed with notices.

Pnyx makes up to three attempts to assemble memory when access, home or project attachments change during the read. If all attempts see changes, the command returns `CONFLICT` without the assembled memory.

Agent event history shows Hydra memory changes only in the caller's own Hydra. Legacy owner-memory changes also require access to `shared`. Saved reviews require read access to their recorded poleis and project attachments. Reviews without source metadata stay visible only to the owner. Task events remain visible.

Explicit cross-Hydra commands proceed with notices outside the caller’s memory scope. Workers start with the target Hydra’s memory. Ordinary memory reads remain filtered by the caller’s native Hydra.

Manage polis names and readers with `settings set --json '{"poleis":{"shared":{"readers":["*"]},"work":{"readers":["hydra-work"]},"personal":{"readers":[]}}}'`. Read the current settings revision and pass `--if-revision`. Include only the poleis you want to change. Use `null` to remove a polis other than `shared`. A reader list containing `*` accepts every Hydra that includes the polis in its read list.

`hydra set --read-poleis shared,work --polis work --hydra hydra-work` changes a Hydra's access. An empty `--read-poleis ''` opts out of all poleis. Use `owner memory move --key <key> --to <polis> --hydra <hydra>` to move a whole document from the resolved write polis to another polis, merging distinct lines in the destination. Moves append one durable entry; old versions remain in the log. Ordinary sets, confirmations, archives and forgets affect the write polis only.

Each project's memory has one assigned polis; existing projects default to `shared`. `project move <name|path> --polis <polis> --hydra <hydra>` changes that assignment without partitioning its memory. Moves outside the caller’s read scope produce a notice. An attached Hydra with access to the project's polis may read and write that project's memory regardless of its owner-memory write polis.

Unreadable poleis and project memory are absent from lists, digests, worker prompts and Oracle results. A local shell with raw disk access can still read the logs.

Access edits and explicit memory writes apply directly. Widened visibility and writes outside read scope produce notices with the commands that change the settings. The server checks access again before writing and checks both memory revisions for note moves. The `memory` field in `owner memory list` combines every readable polis. To edit the home polis, use the `writable` documents and pass their revision unchanged with `--if-revision`.

Ordinary memory reads use the caller’s native `PNYX_HYDRA` and may return filtered or empty memory. Explicit writes to another Hydra proceed with notices.

`pnyx-axi hydra remove <id> --hydra <caller>` runs directly. Every caller is refused deletion of copies containing unlanded work. Removing the caller or last Hydra produces a notice. Settings runs the same command. See the [CLI guide](../../../docs/pnyx-axi.md) for cleanup, retention, safeguards and recovery.

Use `project list`, `project show <path>` and `project remove <path>` to manage the Hydra's own attachments even when `readPoleis` is empty. Ordinary memory reads require polis read access.
