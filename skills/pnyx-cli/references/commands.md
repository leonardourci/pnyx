# Pnyx

## Names

Pnyx is named after the hill in Athens where the citizens' assembly met to decide. Three names follow that theme, and they are the same in the app, the docs, the CLI and the code:

- **Pnyx**: this app, where every agent and its work is shown.
- **Hydra**: an orchestrator, many heads and one body. Each Hydra has its own columns and tasks, and creating a Hydra creates them.
- **Oracle**: the search field. Search it by keyword; it returns matching tasks, messages, settings and actions, never made-up answers.

Everything else uses its plain name: actions, Settings, History, Focus mode, Hydra's memory, columns, tasks, subtasks, workers, briefs, conversations and comments. Column names are the user's own. Do not invent other themed names.

Run `pnyx-axi` for the Hydra summary and `pnyx-axi --help` for commands. Pnyx is pre-v1: cards come from `pnyx-axi push`, from `pnyx-axi firstmate sync --home <path>` and, after `pnyx-axi setup hooks`, from Claude Code and Codex sessions. Hook events wait in the spool until the next write ingests them. `pnyx-axi oracle "<words>"` finds past work across card titles, links, events and notes by keyword, matching word forms, synonyms and near spellings. Results rank by the query words in a card's title, project and link titles, then by its best-matching entry with notes counting double. Saved task briefs, intents, owner asks and investigation reports remain searchable after edits. Read the latest stored report with `task report <task>`. Helper results match their tasks; unchanged helper waits are omitted. `pnyx-axi card <id>` shows a card's summary, decisions and context, harvested from what sessions, Firstmate and linked pull requests already recorded.

When a session waits on its own question, permission or plan prompt, `pnyx-axi card <id>` lists the request with its options and `pnyx-axi reply <id> --answer <request key> --json <answer>` answers it in that session's tmux pane (see `pnyx-axi reply --help`).

When Hydra relays an owner's chat answer to a task question, `pnyx-axi reply <task> --question <question> --from-message <owner-message> --text "<relay>"` records the answer with the outgoing message before delivery. Go/Hold and Merge/Hold questions also take `--choice`. An answered merge Hold can be replaced by `task answer <task> <question> --from-message <owner-message> --choice Merge` only when the saved owner message postdates Hold and tells Hydra to merge that PR. Undo restores Hold. Hydra can instead use `task reask <task> <question> --reason "Confirm the merge again"` to restore the review controls on the card; this grants no approval until the owner answers Merge. A plain reply leaves task questions open. A failed delivery can be retried with the same `--idempotency-key` without changing the saved answer.

To start a worker for a task, run `pnyx-axi task start <task>`, which has the Pnyx server run Claude Code or Codex according to the task kind, with `--harness claude|codex` or `--account <registered name>` to override it, or add `--via paseo|firstmate|command` (see `pnyx-axi task --help`). Hydra follows the `pnyx-orchestrate` skill and the workers it starts follow `pnyx-report-progress`; `pnyx-axi setup hydra --home <firstmate home>` gives it to a Firstmate home.

`account set <name> --provider claude|codex --folder <path> [--label <display name>]` registers an existing Claude Code or Codex home; Pnyx stores the home, never credentials. A candidate's `account`, or `task start --account <name>`, runs on exactly that login and never on another. Each provider and account pair appears once per rule. The routine helper has its own account, set with `settings set --json '{"helper":{"harness":"claude","account":"claude:work","model":"sonnet"}}'`; leave it alone when changing the main Hydra's selection. See [named accounts and dispatch](../../../docs/pnyx-axi.md).

For related local task changes, prefer one `pnyx-axi apply --file <path|-> --hydra <hydra>` over separate calls. Its versioned JSON document contains `changes` and optional `expected.tasks` revisions; `--check` previews changed fields and collection counts; `--check --full` previews complete records without writing. Supported operations are `task.create`, `task.brief`, `task.owner-ask`, `task.depend`, `task.undepend`, `task.status`, `task.hold`, `task.release`, `link` and `outcome`. `intent` on `task.create` or `task.brief` sets the card's goal; `task.owner-ask` keeps the owner's exact words separately. A create's `as` alias can be used later as `$alias`. Keep the document and `--event-id` unchanged on retries. All changes, including lifecycle effects, commit together; invalid input writes nothing. Correct batches with another apply, since undo refuses their child events. Starts, messages, memory and settings stay separate. See [the operation schema](../../../docs/pnyx-axi.md#atomic-local-changes). Heads dispatch rules and accounts change the same way through `pnyx-axi rule apply --file <path|-> --hydra <hydra>`: the document holds `expected.revision` from `rule show` and a `patch` naming only what changes; `--check` previews it, then the same command without `--check` applies it directly and records a line in chat. Permission increases still need the owner through `--propose`, even in Bypass permissions.

Tasks can keep instructions before an agent exists: `task create --title "<title>" --brief "<instructions>"`, then `task brief <task> --brief "<instructions>"` to edit them. Starting or explicitly attaching an agent hands it that brief. `task hide <task>` and `task unhide <task>` change visibility while preserving the record. `task move <task> --to-hydra <hydra> --reason "<why>"` moves a task to another Hydra with its record, history and Pnyx-run worker; the task copy stays in place. A refusal names the command that clears it (attach the project, wait for the turn, detach an outside session, unqueue, undepend, end a wait), and `undo` points to moving it back. Task and agent operations record their lifecycle facts and place cards with worker declarations. Column descriptions (`column list`, `column describe <id> --description "<when and why>"`) guide manual moves, reserved for owner requests or exceptional corrections with a reason. CLI card moves and column moves/deletes return a confirmation token first; repeat the exact command with `--confirm <token>` to act. `column resize <id> --width <pixels>`, `hydra resize --width <pixels>` and `layout reset [--all]` let Hydra adjust the layout. Settings every Hydra shares (theme, text sizes, cards and chat switches, keyboard bindings, default widths, Hide Done, review cadence, routine helper, whether the Oracle keeps its filters, the Hydra list's order, the diagnostic logs' level, days and size cap) are read with `settings show` and changed with `settings set --json '<patch>'`, naming only the keys that change. `owner memory list|set|forget|move` keeps the owner's preferences and learnings in the Hydra's write polis, and `hydra memory list|set|forget` what only one Hydra needs.

A restart or upgrade stops Pnyx-hosted agents; a turn it cut resumes from its saved session when the server is back, and a pending permission request expires, so the agent asks again. Never restart Pnyx to clear a blocked turn. Reconcile unknown answer delivery through its existing receipt.

`pnyx-axi page` summarizes the Hydra as a page shows it; `--full` prints all of it and can be megabytes, so read tasks with `task list` and `card <id>`.

For diagnosis, `pnyx-axi debug timeline --task <task> --hydra <id>` returns bounded identities without conversation bodies; `--message`, `--batch`, `--session` and ISO time filters narrow it. Continue with the returned cursor and the same filters. `debug health` reads current ownership, unsettled inputs, helper completion/deadline facts, spool age and recovery attempts. Unknown means unavailable, not permission to resend or release ownership. Safe failed-message recovery is bounded to two logged attempts using the original idempotency key; inspect its recorded outcome before acting. For slowness, `debug performance` reads the diagnostic logs of the last hour (`--since`, `--until`, `--operation <prefix>`): each action's count, typical and worst duration, errors and warnings, the server's memory over time and the slowest actions. `logs` gives the local JSONL folder and retained sizes. Timed lines include `startedAt`, `at` and `ms`; periodic `process` and `storage` lines include RSS, heap, CPU, loop lag, active resource counts and database/log bytes. Detailed mode adds successful HTTP requests and fast event reads. Logs omit hook payloads and arbitrary error text; error fingerprints, codes and call sites group failures without retaining messages.

For an exact past reply, use `pnyx-axi hydra message --id <message-id> --before 3 --after 3 --hydra <hydra>`, or `task messages <task>` with the same options for a task thread. Select by `--seq <seq>` or `--at <ISO-time-with-timezone>` instead when needed. A selector alone returns one message; `--budget <tokens>` grows its surroundings. `--direction older|newer` pages before or after it, excluding that message, and `--from <seq|ISO-time> --to <seq|ISO-time>` selects an inclusive range. Follow `older` or `newer` with `--cursor <cursor>`; cursors pin the thread, range and snapshot. Pages contain whole messages within the token, count and byte limits. Hydra references stay valid across inscribe, compaction and agent switches; a task's lookup reads its current session and the owner's replies, and `task chat <task> --session <session>` reads a past one. A reference whose transcript is gone returns `NOT_FOUND`. Owner comments include the command for their Hydra and thread; use it, then follow cursors only as far as needed.

Owner questions persist across completed investigations, worker exits and unrelated merges. Use `task discuss-question <task> <question> --text "<clarification>"` to discuss without answering. Short “why?” and “explain” requests are discussion. Longer instructions remain answerable; use `discuss-question` for other follow-up wording. The owner can choose Later with `task defer-question <task> <question> --until "<future time>"`; Hydra needs `--from-message <owner-message>` with the owner’s newer instruction. Deferral pauses active attention and reminders, preserves the gate, and returns at the date. Ready for review controls on linked cards share one canonical Merge/Hold approval per PR URL. Task questions stay on their cards; only blockers and tasks the owner explicitly selects or mentions also appear in chat. Use `hydra ask --question "<question>" [--context "<why the owner is needed>"] [--choice "<label>"]` for a real owner decision with no task; it lives in chat. Workers send procedural questions through `task ask` to Hydra, which routes helper work. Hydra announces decisions already settled by the owner’s words in one `hydra send --task <task>` line, which also records them on the card. Automatic question reminders use one grouped chat line at the existing four-hour cadence.

`task refresh-links <task>` asks the server to read its open pull requests now, answering `none` when it has none. Otherwise they are read once per minute while the worker works or checks are pending and every 15 minutes when idle; a failed read keeps that schedule, and a link that resolves to no pull request three times waits for a task or link change.

`debug cpu-profile --seconds 10 --out ./idle.cpuprofile --hydra <id>` samples the server's main thread and returns the hottest functions. Only one capture runs at a time; the output file is private, and server shutdown cancels the capture.

Stop a hosted worker with `task stop <task>` or Hydra with `hydra stop`; a worker's own request is refused, so ask Hydra with `task ask`. Stop cancels the owner's unread inputs; they remain visible as Not delivered: stopped. Use `task send-now <task> <message-id>` or `hydra send-now <message-id>` to interrupt a step for a queued message, and `hydra cancel <message-id>` to cancel one message held behind a compaction, an upgrade or an agent change. After Stop, routine wakes wait for the owner's next message.

Hide Hydras from the page list and switcher with `settings set --json '{"hiddenHydras":["hydra-2"]}'`. Restore all with `settings set --json '{"hiddenHydras":[]}'`. This shared view setting leaves pages, projects and workers running.

`task merge <task>` checks the task’s merge rule, owner approval, classic protection and reported checks, and binds the request to the verified head. A 403/404 from the branch-rules endpoint means no readable rules there; other evidence failures still refuse the merge.

### Poleis

Hydra config uses `polis` for its home and `readPoleis` for its read list. The defaults are `shared` and `["shared"]`. Change the read list separately with `--read-poleis`.

`shared` holds existing owner memory without rewriting its log. New and existing Hydras read and write `shared` by default. `work` and `personal` start empty with no readers. Owner-memory reads merge only poleis allowed by both the Hydra reads list and the polis readers list. Writes resolve the Hydra's one write polis on the server; ordinary memory commands accept no polis argument. The 24000-character budget applies to each polis.

Manage polis names and readers with `settings set --json '{"poleis":{"shared":{"readers":["*"]},"work":{"readers":["hydra-work"]},"personal":{"readers":[]}}}'`. Each named polis updates independently; use `null` to remove a polis. Omitted poleis stay unchanged, so a Hydra can edit its visible poleis without deleting hidden ones. `shared` is reserved and cannot be removed. `*` allows every Hydra through the polis lock; the Hydra's reads list must still allow it. Read the current settings revision before editing and pass `--if-revision`.

`hydra set --read-poleis shared,work --polis work --hydra hydra-work` changes a Hydra's access. An empty `--read-poleis ''` opts out of all poleis. Use `owner memory move --key <key> --to <polis> --hydra <hydra>` to move a whole document from the resolved write polis to another readable polis, merging distinct lines in the destination. Moves append one durable entry; old versions remain in the log. Ordinary sets, confirmations, archives and forgets affect the write polis only.

Each project's memory has one assigned polis; existing projects default to `shared`. `project move <name|path> --polis <polis> --hydra <hydra>` changes that assignment without partitioning its memory. Both source and destination must be readable. An attached Hydra with access to the project's polis may read and write that project's memory regardless of its owner-memory write polis.

Unreadable poleis and project memory are absent from lists, digests, worker prompts and Oracle results. A local shell with raw disk access can still read the logs.

The owner applies access edits immediately. Hydra may narrow access directly. Widening a Hydra reads list, adding polis readers, or moving a project, document or learning to additional readers requires the owner's Confirm, even in bypass modes. Repeat the refused command with `--propose` to save a question in Hydra's chat; the change waits until the owner confirms. Changes to the target or its access rules invalidate a pending proposal. Note moves also pin the source and destination revisions (`--if-revision` and `--if-destination-revision`), checked under the move lock. `owner memory list` separates the combined readable `memory` from the current home polis documents under `writable`; edit the latter when inscribing. Pass the printed revision unchanged; it also guards against a home-polis change.

Agent memory reads, writes and proposals are bound to the caller's native `PNYX_HYDRA`. Naming another Hydra returns empty memory or `NOT_FOUND`; task visibility and owner targeting keep their existing behavior.
