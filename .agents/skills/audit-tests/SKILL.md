# Audit tests

A test must pass unchanged when the implementation is renamed or rewritten with the same behavior, and go red when that behavior breaks. If a behavior-preserving change forces a test edit, the test is brittle: recommend rewriting it against visible behavior or deleting it. This audit checks that every core behavior in scope has regression coverage. Use the PR's Intent, changed behavior and any tests the branch edited as the scope unless a wider area was requested; when the requester names the behaviors they consider core, start from that list. Read `docs/testing.md` for the test harness.

- [ ] Inventory behavior as “when X happens, Y results”. Include success, refusal, invalid or empty input, failure, recovery and restart when relevant. For Pnyx, cover permissions, event persistence and replay, worker lifecycle and reply delivery where touched. If a behavior can't be phrased that way yet, keep narrowing until it can.
- [ ] Map each requested behavior to a test and its observable assertion through the feature's public surface: CLI output and exit status, persisted events, server responses, delivered replies or the rendered page. For live agent behavior, also require isolated validation with real agents. Rebuilt history or a mocked view alone does not cover live behavior. A behavior with no test is the top finding. A test that names the behavior but asserts something else is the same gap.
- [ ] Run the flip test for each core flow and each new or changed test in scope: in a throwaway copy, invert a condition, omit an event or delivery, or return the wrong result. Run the relevant test and confirm its behavioral assertion goes red, then discard the copy. A regression test must fail with the fix reverted in that copy. For each bug fixed in the area's recent history (`git log`), check that such a test exists.
- [ ] Reject tests that grep, regex-match or snapshot source text. Reading implementation files to assert spelling, helper names or code shape does not exercise behavior. Invoke the real function, CLI, server or page instead. Snapshots of outputs are useful only when the output itself is the contract and a behavioral break changes the assertion.
- [ ] Assert behavior from the user's point of view, through public APIs (the CLI, server, events and rendered state), not code structure. Reject tests that call private helpers or mock Pnyx's own modules.
- [ ] Keep logic out of tests: no loops, conditionals or calculations that build the expected value. Write expected values literally.
- [ ] Remove brittleness from assertions on incidental copy, log order, private helper calls or timing. Flag tests the branch edited even though the behavior they cover stayed the same. Wait for an observable condition with a bounded wait; do not use fixed sleeps or retries to hide a race.
- [ ] Register completion observers before triggering work. For absence, drain the named operation; for domain deadlines, control time and assert just before and at the boundary. Force race phases with gates instead of repeated scheduling attempts or PID order.
- [ ] Keep process isolation and sequential tests within each file while environment and filesystem mocks are global. Restore mocks and close owned resources.
- [ ] Reject unbounded waits, including `for (;;)` and `while (true)` polling without a deadline or attempt limit. Bad: `while (true) { if (await ready()) break }`. Good: `await waitFor({ ready, timeoutMs: 5000 })`, where timeout fails with the last observed state.
- [ ] Do not match exact event sequence numbers read in separate operations: another writer can append between reads. Bad: `assert.equal(reply.seq, previouslyRead.seq + 1)`. Good: find the reply by its returned ID in one event snapshot, then assert its payload and causal link.
- [ ] In tests, use IDs returned by setup or the operation under test. Bad: `taskShow({ id: 'task-1' })` after creating a task. Good: `taskShow({ id: created.id })`. Fixed IDs belong only in synthetic input whose identity is the contract.
- [ ] After mechanical import-path updates, moving code between files should leave behavioral assertions unchanged; flag assertions about implementation location or private helpers.
- [ ] Put a test in its area's `tests/<area>.test.ts`, through the real server, `pnyx-axi` and the page's data calls; call a function directly only for a tricky edge case the server cannot reach cheaply, in the same file. Add a browser journey in `tests/e2e/` only for what needs a real page (rendering, scrolling, live updates); check other page changes in the local preview and the pull request's screenshots. A core behavior covered only by tests over mocks that reimplement Pnyx is a gap: the test proves the mock.
- [ ] Isolate every test with temporary `PNYX_HOME`, random ports and synthetic fixtures. Never access real user folders, tools, services or accounts. Fake external services at their boundary; a test that needs the network is a finding, not coverage. Remove inherited worker identity in owner-CLI subprocesses.
- [ ] Prefer real dependencies over fakes: use the real file system, event log, server or SQLite through a temporary `PNYX_HOME` rather than mocking them. Fake only at the outer edge: third-party services, AI providers and the network.
- [ ] Use property-based tests (fast-check) for tricky pure logic with many possible inputs, such as the reducer or parsers. Run mutation testing (Stryker) only as an occasional audit to find missing tests, never in every run.
- [ ] Reproduce a bug in a failing test before fixing it, and confirm the test passes only with the fix.
- [ ] Fold a new test that fits an existing test into assertions in that named test. Fold several tests, new or existing, that set up the same flow or real system (such as a server or database) into one flow test that touches everything once. Map and carry over every unique assertion before folding; keep coverage of each affected CLI, transport or restart boundary.
- [ ] Give every test in scope a verdict: keep (name the regression it catches), fold into `<named test>`, or delete (name what still covers the behavior, or say “nothing does”). Keep only tests for behavior a user would notice or a named past bug; delete tests kept just in case. Flag incidental timing, internals or implementation details, duplicates of a better test, and doubtful tests that have flaked.
- [ ] Run focused tests and the suites selected by `pnpm verify` before readiness. Respect explicit test holds; record pending suites and known failures without changing unrelated tests or claiming a pass.

Report a short behavior-to-test mapping, every test’s verdict, gaps and brittle tests. Treat a core behavior with no behavior-level test, a brittle test standing in as its only coverage, and a test that touches real user data or services as must-fix; level changes and merging redundant tests are recommendations. For each gap, name the file, the behavior as “when X, Y” and the assertion that goes red when it breaks. Record each flip, the test and assertion that went red, and what else ran, passed, failed or remains pending. Once complete, tick **Ran `audit-tests`** in the PR and describe what you fixed (or say no findings). The audit can be complete while a suite is pending; pending suites still prevent a verification marker.

For an agent: inspect assertions and exercise the behavior yourself. Never edit, commit or push the audited branch; make behavior-breaking probes only in throwaway copies. Do not substitute a source-text search or a list of test filenames for the audit.
