# Provider sessions

Claude Code and Codex run under `pnyx-axi serve`. Stopping or restarting the server ends their running turns. The provider interface separates execution from readers inside that process.

`Provider.open` returns a `HostedSession`. Its first `run` binds application input and permission handling and starts one native owner. `attach` adds an event reader. Returning from a reader removes that subscription; `close` explicitly shuts down the native session. A slow reader has a bounded queue and receives an error if it falls behind. Attachments receive live events; `snapshot` supplies current work, permissions, value-free answer receipts and the latest complete terminal outcome. This is an in-memory snapshot, without a durable replay or acknowledgement protocol.

Inputs have an application ID, text and an explicit image manifest containing paths, media types and SHA-256 digests. The application selects images from the original message, before adding memory, helper outcomes or other context. Adapters translate only supplied parts and check their bytes before delivery. Missing or changed images fail visibly. Claude uses a native UUID mapped back to the application input ID; Codex associates accepted starts and steering with their turn IDs. An input receipt can carry the harness's own intake time (`InputReceipt.at`). Claude's comes from its transcript: the user line of a message that opens a turn, or the queue removal of one folded into a running turn. Codex's receipt arrives as it starts or steers a turn with the input, so it carries no time and Pnyx times it on arrival; a Codex input carried into the next turn stays unsettled until that turn confirms it.

Native permission IDs are separate from the saved Pnyx permission ID. An answer receipt records `received` when application policy returns its decision and `submitted` when the adapter hands it to the SDK callback or Codex pipe. Submission does not prove native application. Receipts contain no answer values. The application owns authorization, persistence, redaction and expiry.

Each `turn-ended` fact carries its completion time, input IDs, status, final text, assembled assistant messages, structured output, usage and any error. The helper parses this complete outcome. Input, permission, answer, terminal, compaction and structured-output events are critical facts; text, tools, thinking, usage, work and foreground activity are view events.

A worker card stays working while its session has native background work or one of its own hook-reported child agents is working, even after its foreground turn finishes. Hook-reported children are matched by provider and parent session ID; ordinary subtasks and other sessions do not contribute. Ended workers remain stopped, and a child that has finished or ended no longer contributes activity. Foreground `finished` does not authorize idle cleanup. Cleanup requires no running turn or tool, unsettled input, pending control, queued native turn or background task. Claude's queue count and background-task replacement sets supply native knowledge; missing queue information keeps the session open. A Codex input refused by steering remains carried until its own turn settles. Codex child agents block cleanup until confirmed shutdown; background commands and unsupported native work also keep their owner open. Explicit close and server shutdown retain their existing authority.

The Claude SDK warning about a shadowed permission callback is logged at most once per server process. The callback stays installed so permission-mode changes keep their existing behavior; other SDK warnings remain visible.

## Transcript records

`src/workers/claude.ts` and `src/workers/codex.ts` decode their own transcript formats into `TranscriptRecord`, defined in `src/workers/provider.ts`. `src/workers/transcripts.ts` selects the reader through `readTranscriptRecord`. Records carry the message role and time, visible text, hidden wake boundaries, tool and thinking traces, calls and results, harvested notes and observed settings. Calls carry normalized command, file, query, URL, skill and description fields. Trace positions retain their original block indexes so thread entry IDs and pagination stay stable.

The thread reader, latest-message feed, reply confirmation and hook harvesting consume that neutral shape. Redaction and display limits stay in their consumers. The browser imports the shared text and call presentation helpers; its bundle does not load the provider adapters.

Hydra chat retains assistant commentary, tool calls and results across quiet endings and history paging, read from the native transcripts of every session Hydra was configured with: older pages continue into the previous session, and the cursor names which one. Progress folds precede the reply they led to. Equal timestamps use native record positions to keep a tool result before its reply. Hidden inputs remain turn boundaries and never appear as owner text.

An explicit thread read returns a full page, including initial load, Older messages and reconnect. Unsolicited Hydra and worker chat updates carry entry-ID additions, replacements and removals, plus changed fold and timing records. Each page has a stream and version; a missing version causes the page to request a fresh page. Unchanged entries retain their browser objects so existing message rows can skip rendering. When the owner returns to the bottom, the page requests the three most recent source pages over the existing thread socket route. The server then keeps that window bounded on new arrivals; scrolling away, selecting message text or focusing a message control retains the range being read. Older messages reload by cursor, and revealing an evicted comment reloads its source first. This bounds loaded transcript pages. The page keeps no Hydra message history: chat loads only through these thread pages, and the page reads only the owner's latest message to Hydra, through Zero's `hydra.ownerMessage` query.

Redaction happens before transport offsets are assigned, so a later read cannot shorten a chunk and break its rejoining. Streaming plain text includes the last received word while incomplete Markdown stays held until it can render. The saved transcript replaces live text without a second message.

## Usage

Each provider's adapter reads usage from its own transcript format and emits neutral `HostedUsage` events for live readings; `src/workers/usage.ts` picks the transcript reader by harness. Consumers never interpret vendor fields. `src/workers/usage.ts` combines those readings, recorded task totals and quota plan windows into `AgentUsage`. The server pushes that derived shape over the existing WebSocket; both the composer and task card render `web/src/workers/usage.tsx`. The browser keeps spend and usage in a separate live map and merges them into the displayed cards; its saved Hydra state contains only confirmed event state.

Current context is the latest request's reading, not the sum of earlier requests. Recorded task tokens retain their worker and attributed Hydra breakdown. Only reported counts are shown. Claude transcripts provide used tokens but no window or session cost; those details can come from live readings. Synthetic assistant records do not change usage, and a transcript compaction boundary clears current context. Transcript fragments and task totals never substitute for current context.

The server owns transcript readings and task totals and passes them to the host for reads and views. `hydra usage` returns that shape once. `hydra usage refresh` refreshes plan windows separately; `--force` bypasses the quota cache.

## Task tool grants

Hosted Hydra sessions, workers, investigations, summaries and model probes start with no external MCP servers or plugins. Ordinary harness shell/file tools and repository skills remain available. The routine helper keeps its bounded tool and skill set. Pnyx applies these defaults when starting or resuming either harness; it does not edit login or project configuration.

Hydra chooses task additions with repeated `task start <task> --tool <capability>` flags. For UI work, select `browser`: Pnyx gives the worker a named, isolated, headless `chrome-devtools-axi` session and instructions to stop it afterward. It clears inherited browser URLs, profiles and connection settings for this capability. No second browser server starts automatically.

Start-only additions configure the provider without changing the saved selection first. The attachment and grant commit together through the existing event transaction. A failure or crash before that commit leaves earlier grants intact; a retry uses the current recorded selection.

Failed tool reopening uses the host's existing delays and stops after as many attempts as there are delays. A new grant revision resets that bound; waiting for a hold or copy cleanup does not spend an attempt.

`task tools <task> --available [--harness claude|codex] [--account <name>]` lists configured capability names without their commands or credentials. An unstarted task needs a harness. `task tools <task>` lists its grants. Names are `browser`, `mcp:<configured-name>` and `plugin:<installed-id>`. Plugin grants include that plugin's configured MCP servers; other plugins and servers remain excluded. Claude selects the applicable installed plugin scope and loads its MCP definitions explicitly while suppressing automatic plugin MCP discovery. The catalog leaves out what the owner turned off: a project `.mcp.json` server appears only once approved in Claude Code (`enabledMcpjsonServers` or `enableAllProjectMcpServers`) and never once rejected (`disabledMcpjsonServers`), and Codex servers and plugins set `enabled = false` do not appear. A start, and a change of Hydra's own agent, is refused before it switches when the target login lacks one of the task's saved grants; the error names the revoke command.

A worker asks Hydra with `task ask <task> --question "I need <capability> to <action>"`. Hydra grants or revokes it with `task tools <task> --grant <capability>` or `--revoke <capability>`; flags may repeat. Hydra makes this decision itself, with no new owner approval step. A grant enables a tool; it does not authorize writes by that tool. Pnyx refuses grants from requests identified as workers, including a worker overriding the command actor. Any agent running as the same user can set `PNYX_ACTOR`; these are cooperative roles.

Pnyx records each selection in the event log, waits for native turns, tools, background work, queues, pending controls and accepted inputs to settle, then reopens the same saved conversation with the selection. It confirms application after the replacement accepts input. Pending grants recover after restart. Discussion holds block tool changes; a previously pending grant waits for release. Pending application also waits for copy settlement and resumes afterward if its session folder remains available. An unavailable capability fails visibly without restoring inherited defaults. Grants belong to the task; another task starts empty. Outside launch routes retain their own configuration and refuse dispatch tool flags.
