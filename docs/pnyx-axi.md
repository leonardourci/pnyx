## Output and errors

`pnyx-axi` follows [AXI](https://axi.md/): it prints [TOON](https://toonformat.dev/) on stdout, never prompts, and keeps everything an agent needs on stdout.

- Bare `pnyx-axi` prints the Hydra summary: the executable, server state, attached projects, cards per column and the first cards.
- `pnyx-axi <command> <subcommand> --help` prints that subcommand's usage and notes; `pnyx-axi <command> --help` prints the whole command.
- Lists show a few fields per row and the total, such as `count: 20 of 85 total`. `task list` shows id, title, project and column; `--fields status,worker` adds more.
- Detail views cut long text to 1,000 characters and say how long it was, such as `… (truncated, 4200 chars total)`; `--full` shows the whole record.
- An empty answer is explicit, such as `tasks: "none: no tasks on this Hydra"`. A write that changes nothing, such as attaching a project that is already attached, returns `event: "none: unchanged"` and exits 0.
- Errors print on stdout as `error`, `code` (`VALIDATION_ERROR`, `NOT_FOUND`, `CONFLICT` and others) and `help` lines with the command that fixes them. An unknown flag is named and the subcommand's valid flags are listed.
- Exit codes: 0 for success and no-ops, 1 for errors, 2 for usage errors.
- `help` lines suggest next commands, carrying `--hydra` forward and leaving runtime values as `<id>`.
- Writes take `--event-id <id>` as an idempotency key and `--if-revision <n>` for an expected revision. Risky changes return a token to repeat with `--confirm <token>`.

The reporting hooks print nothing, except at session start: in a folder inside an attached project, they print that project's open tasks (`pnyx-axi context`) into the new session. Agents learn the commands from the `pnyx-cli` skill (`pnyx-axi setup skills`).

## Install

Needs Node 22.13 or newer and pnpm (the version pinned in `package.json`).

To run agents, install and sign in to [Claude Code](https://code.claude.com/docs/en/overview), [Codex](https://developers.openai.com/codex/cli/), or both. Configure the [dispatch rules](#starting-workers-and-hydra) for the harnesses and models you use. GitHub integration needs [GitHub CLI](https://cli.github.com/) (`gh auth login`) and [gh-axi](https://github.com/kunchenguid/gh-axi) on PATH; account quota ranking uses [quota-axi](https://github.com/kunchenguid/quota-axi). The login service (macOS or Linux) and terminal integrations are optional; the foreground server does not need them.

```sh
git clone https://github.com/leonardourci/pnyx.git
cd pnyx
pnpm install
pnpm run build
pnpm add -g "$PWD"
pnyx-axi --version
pnyx-axi setup skills
```

If pnpm reports that its global bin directory is missing from PATH, run `pnpm setup`, reopen your terminal and retry `pnpm add -g "$PWD"`. `pnpm add -g` links the clone, so `pnyx-axi upgrade` (see [Upgrade](#upgrade)) is all an update needs. `pnpm link --global` does not work with this pnpm; use `pnpm add -g "$PWD"` (or `npm install -g .`). Without a global install, run `./dist/cli/pnyx-axi.js` from the clone.

Setup commands for hooks, skills and the login service change user-wide configuration. They refuse a `PNYX_HOME` other than `~/.pnyx`, including previews and removals. Unset `PNYX_HOME` to use the default home, or pass `--allow-custom-home` to explicitly target another home. Installing its service also requires a `--port` that no other Pnyx home’s installed service uses; the override does not bypass that check.

`pnyx-axi setup skills` installs only `pnyx-report-progress` and `pnyx-cli` as links into `~/.claude/skills/` (or `$CLAUDE_CONFIG_DIR/skills/`) and `~/.agents/skills/`. Workers in any project or copy can report to their card and use the CLI. The links point to this installation, so updates apply without copying skills into projects. Keep the installation in place; rerun setup if a link is missing. Setup also removes legacy global skill links when their targets belong to a Pnyx installation. Existing files and unrelated links are preserved; move a conflicting skill aside before installing. Use `pnyx-axi setup skills --preview` to inspect changes and `pnyx-axi setup skills --remove` to remove this installation's global links and legacy Pnyx links. Check readiness with `pnyx-axi integrations` or Settings > Integrations.

Every Hydra offers the `inscribe` and `pnyx-set-up` skills and the `/upgrade` and `/restart` commands in the composer's **Built-in** section, including Hydras with no attached projects or no session yet. Built-ins remain available while discovery is loading or unavailable; close and reopen the menu to retry the other catalogs. Ask Hydra to save its memory in plain words or choose `/inscribe`; add a project name to curate that project's memory. The other Hydra skills (`pnyx-orchestrate`, `pnyx-arrange-columns`, `pnyx-manage-workers` and `pnyx-firstmate-as-hydra`) stay installed in Hydra's own folder, hidden from the menu, and load only when their contract's trigger applies. Project skills remain associated with their project. Choosing a built-in reads Pnyx's shipped skill explicitly, so a global or plugin skill also named `inscribe` keeps its own entry and cannot replace it. Firstmate setup refuses to overwrite an owner skill in its local Hydra skill folder; move that skill aside before retrying setup.

User data lives in `~/.pnyx` by default. Set `PNYX_HOME` to keep it anywhere else; the clone holds only code.

You do not have to set everything up before the first Hydra. Each time a Hydra session opens, Pnyx checks the local dispatch config, Claude and Codex logins, hooks, global skills, quota-axi, the login service and a profile for each attached project, and puts only what is missing in Hydra's digest as a short "Setup needed" list (a complete setup adds nothing). Hydra creates the local config and writes project profiles itself, and raises the owner-only steps (hooks, skills and the login service) as questions in its chat that run only when you Confirm. `pnyx-axi setup check` prints the same list in a terminal and exits 1 while anything is missing.

For a trial with separate data, run `PNYX_HOME=/path/to/trial pnyx-axi serve --port 0`; `0` picks a free port and the output gives its URL. Use that same `PNYX_HOME` for later commands, including `stop`. A separate data home still uses your normal harness logins and global skill folders; setup previews show which user-wide files would change. See [Run](#run) to start your everyday Hydra and [CONTRIBUTING.md](../CONTRIBUTING.md) to work on Pnyx itself.

## Projects

A Hydra can work across several projects. Each project is a folder on your laptop, shown by its folder name. Attach an existing folder or clone code into a destination you choose:

```sh
pnyx-axi hydra create work
pnyx-axi project add /path/to/project --hydra work
pnyx-axi project add --clone https://example.com/team/project.git --into /path/to/new-project --hydra work
pnyx-axi project list --hydra work
pnyx-axi task create --title "Ship the change" --project project --hydra work
pnyx-axi task project <task> --project project --hydra work
pnyx-axi project set project --copy '<shell command>' --hydra work
pnyx-axi project set project --landing pr --merge owner --hydra work
pnyx-axi project remove project --hydra work
```

Clone runs ordinary git directly, without sending the URL to an agent. `--into` is required. Relative paths are resolved from the CLI's working folder; in the UI, type an absolute laptop path or start with `~/`. Removing a project only detaches it: tasks, history and the project record stay. Add its path again, or choose Re-attach under Settings → Projects → Detached, to bring it back. Use a full path when folder names are ambiguous.

After a confirmed pull request merge, Pnyx refreshes the task's attached ordinary project copy. It discovers the configured remote's default branch and fast-forwards only a clean copy already on that branch. Dirty or untracked files, detached heads, feature branches, local commits outside the remote default, and locks are preserved. Task history records the observed refs and a current, advanced, needs-attention or unknown result; failures wake Hydra with the reason and a manual next step while the pull request stays merged. Refreshes sharing a repository are serialized, and a saved merge proof resumes an unfinished refresh after a server restart. Current and advanced results stay quiet. Git commands have a 30-second timeout; Pnyx never removes an existing refresh or Git lock. The checkout running Pnyx is left untouched, including when attached through a symlink; use the upgrade-available hint and `/upgrade` to pull, build and restart together.

Projects are added by asking Hydra. **Add project** (right-click a Hydra in the left panel or its chat header, type `/add-project` in the composer, or use the **Add a project** link in an empty Hydra's chat) writes `Add @ to this Hydra and ‹what you want done›.` into the composer under any draft, with the project and folder picker open at the `@`. The picker lists this Hydra's projects, then Folders: projects in your other Hydras, folders your agents worked in, typed paths (`~/…` or `/…`) and **Clone** for a pasted git URL. Enter or Tab picks without sending. In the request the folder goes in as its plain path, shown as a gold badge, so the caret moves through it like text and the goal stays editable. A typed path completes like a shell: Tab extends it as text, and Tab again, Enter or moving the caret off a path that names a folder adds it; the caret moves to the optional goal, where Tab fills a suggested prompt or you type your own, and a goal left empty is dropped. Click a picked project to change it. Enter sends the message, and Hydra runs `project add` (or `project add --clone`), asks you when another Hydra already uses the folder, and then does what you asked. `@` anywhere in a message offers the same Folders group. Workers normally get their own copies; only one Hydra at a time may have a worker editing the shared folder itself.

Settings → Projects saves each project’s start command with a name and a **Brings its own folder** switch. Check it when the command creates the worker’s folder itself. Hydra’s summary, `project list` and light check include these settings. Save them from the CLI with `pnyx-axi project set <project> --command-name "Local worker" --command '<shell command>' --brings-own-folder true --hydra <id>`; an empty `--command` clears the setting. Hydra assigns the task’s project, then selects that command with `pnyx-axi task start <task> --via command --command "Local worker" --hydra <id>`. It uses the same task environment as the Hydra’s command. Pnyx normally starts it in the task’s own project copy; checking **Brings its own folder** skips that copy and runs the command from the project folder. Hydra can choose `--folder` or `--in-place` explicitly.

Workers start in their task's own copy of its project by default: on the first start Pnyx gives it a git worktree slot of the project (`hydras/<hydra>/copies/<project>-<n>`) on branch `pnyx/<hydra>-<task>`, and later starts of that task reuse it. A slot comes from the project's pool when a clean one is idle, so its ignored files such as installed dependencies stay; the branch starts from the fetched remote default branch. A failed fetch or default-branch discovery stops allocation; projects without origin use their local HEAD. `task start --in-place` works in the project folder itself instead; it is refused while a worker of another Hydra runs in that folder. A project can make its copies its own way: `pnyx-axi project set <name> --copy '<shell command>' --hydra work` runs that command in the project folder with `PNYX_TASK`, `PNYX_TASK_TITLE` and `PNYX_PROJECT` in its environment, and it prints the new folder's path last; an empty `--copy` goes back to git worktrees. A Hydra start command that makes its own folder skips the copy with `hydra set --command-folder own`.

Each project has a landing rule, chosen when it is added (the add box's **Work lands as** and **Merged by**) and changed with `project set --landing pr|branch --merge owner|hydra` or under Settings → Projects. `pr`, the default, means a worker commits, pushes, opens a ready pull request, links it, and uses `needs_you` with its URL when ready metadata is not available yet or Hydra merges it; `branch` means it commits on the task's branch and declares done. `--merge owner`, the default, asks you Merge or Hold on each ready pull request, showing its title, link, latest worker report or status note, and check counts; Merge records your approval for that pull request, closes its question immediately and lets Hydra merge once checks are green; `--merge hydra` lets Hydra merge with `pnyx-axi task merge <task>`, which refuses a draft, a red check or one still running, merges with a merge commit and records it. Required checks are read from classic protection and active branch rules, including their producer apps; missing or unreadable evidence refuses the merge. The request is bound to the verified head commit. GitHub must confirm the merge before Pnyx records it; queued and unconfirmed attempts stay unfinished, retain their copies, and show on the link until the follower confirms the result. A restart resumes confirmation without submitting another merge. A definite GitHub rejection permits a fresh checked attempt; an ambiguous failure keeps waiting for confirmation. You can always merge a green pull request with `task merge`. A different rule for one task comes from telling Hydra, which records it with `task landing <task> --landing pr|branch --merge owner|hydra`. Pnyx writes the rule into every worker's header, so the worker knows where its job stops. `task status <task> done` is refused, with what is missing, while files are uncommitted or the work has not landed by the rule; you can still move the card to Done yourself.

A worker or Hydra can record a dependency wait with `task status <task> paused --wait-for <dependency> [--ready-when task-done|pr-opened|pr-merged]`. The default is `task-done`, using the same completion checks as prerequisites. `pr-opened` accepts an open or merged linked pull request; `pr-merged` requires one or more non-closed linked pull requests, all merged. The server checks recorded state, clears the wait and queues one steer with the dependency and its PR link. A restart preserves the wait and its delivery identity. Discussion holds, paused holds, unanswered questions, permissions, compaction and helper leases still gate resumption. A new declaration replaces the wait; temporary owner gates preserve it until their answer restores the paused state. The card shows `Waiting: <dependency title>`, or the paused note when there is no dependency.

The server follows every open pull request linked to a live task once a minute through gh-axi. A change in its state, checks or comment count is recorded on the link; nothing is recorded and nobody is woken while nothing changes. Failed checks and new review comments wake the task's worker with what happened and the gh-axi command that reads it (it fixes them on its branch rather than replying, so its own replies never come back as news); a worker waiting in `paused` also hears when checks finish. Workers never sit waiting on their pull request. Once every linked pull request of a task has merged, Pnyx declares the task done, which moves it to Done and settles its copy. Hydra makes sure every open pull request has a worker to wake: its digest marks one whose task has no worker, or whose worker ended, as unwatched, and a worker that ends with one open wakes Hydra, as does news on an unwatched one. Checks settling green or red on any open, ready pull request wake Hydra too, whether or not its worker is alive; on a task whose rule lets Hydra merge and whose worker no longer declares working, green checks wake it to merge. The card's pull request link turns coral while a check Pnyx read is failing.

An investigation (`task create --kind investigation`) answers a question or finds a cause before anything is built. Its worker stores its report with `pnyx-axi task report <task> --file report.md`, which keeps it with the task in the Hydra's log, every version included; `task report <task>` prints the latest, and the open card shows it.

Its `done` needs the stored report and an explicit review of its owner choices: `task report-review <task> --report <report-id> --none` for no unresolved calls, or repeat `--call <gated-task>/<ask-id>` for each choice. The report reader prints its id and inventory. Reuse an existing gated task when possible; Hydra asks the owner there with `task ask <gated-task> --from-report <origin-task> --question "<choice>"`, which pins the question to that report version. Completing or hiding the origin never closes these questions; they remain in Waiting on you until answered or closed with evidence. An unanswered linked question prevents its own task from hiding. Replacing a report requires a new inventory before completion, hiding or promotion. Older reports stay intact and need review at their next such transition. Recommendations needing no owner choice create no task.

The investigation copy stays after done so a build can resume in it; Hydra removes it if you decline the build. When it is done, Hydra tells you its findings in a line or two and asks **Build the fix?** on the card; your yes has Hydra run `pnyx-axi task build <task>`, which turns the same task into its build: its worker keeps its context and starts a fresh branch from the default branch, carrying over only the changes the build needs.

Related tasks can wait behind a worker already changing the same files: `pnyx-axi task queue <next> --behind <task|session> --hydra work`. Behind a session or its current task appends; behind a queued task inserts immediately after it. `task reorder <next> --behind <task|session>` changes the order, and `task unqueue <next>` frees a task for another worker. Each task needs the same project and no active worker or copy. Cards stay in Queued with “next for” and their position; the worker's card lists its queue. Use a card's menu to choose a worker, change order or unqueue. Hydra compares the task's area and expected files with live work, queues only actual overlap or dependencies, and starts independent work in parallel.

Record prerequisites with `pnyx-axi task depend <task> --on <prerequisite> --hydra work` (repeat `--on` for several); remove a relation with `task undepend <task> --on <prerequisite>`. Tasks must belong to the same Hydra, and cycles are refused. A prerequisite must finish its existing task-kind and landing lifecycle with no hold or unanswered question. An investigation needs its stored report and accepted completion; a build must land according to its rule. Task detail, the digest and timed review name unmet prerequisites. Direct starts and queued handoffs share this readiness check; independent tasks remain available in parallel. Reopening or holding a prerequisite blocks new dispatch and gives Hydra a fact about any already assigned dependent, without stopping its worker.

The server checks queues every 30 seconds. A worker keeps handling review fixes until all its linked pull requests merge. Without a pull request, the task must be declared done and its commit must land on the default branch. Once idle, the worker gets a fresh branch from the fetched current default branch, the next task's brief, and the same session and isolated folder; managed copy ownership transfers to the next task. Done cleanup retains that folder while the queue waits. Uncommitted work, missing folders, project copy commands or failed branch preparation return the queue to normal Queued with a handoff note. A dead or detached worker, a working or waiting worker stalled for 30 minutes, three completed tasks, or a 2 MiB transcript also releases the remaining queue for Hydra to dispatch a fresh worker. Unknown presence holds the queue. Firstmate-linked Hydras leave assignment and queues to Firstmate.

When a task reaches Done and its agent is no longer working, Pnyx releases its copy if it has no uncommitted changes and its work has landed: its current commit is on the fetched intended base, or a confirmed merged pull request in the same repository and branch covers it and its merge commit is on that base. Squash merges still count after the remote branch is deleted. A merged link alone never covers later local commits; dirty, divergent and unproved copies stay accessible, including after restart. A released slot goes back to the pool for the next task when fewer than two clean idle slots of that project are already there, or when an attached worker still runs in it; otherwise it is deleted with the files git ignores. A slot that an attached worker runs in is never handed to another task, so a follow-up reply resumes the worker in its own folder. The branch always stays, and a copy whose commit is on no branch is never released this way. A copy made by the project's copy command is only released: its folder stays for that command's own tool. Otherwise nothing is committed or removed; the task keeps its copy, flagged, and Hydra gets a message to resolve it. `pnyx-axi task copy <task>` shows the copy and that check, and `task copy <task> remove` checks again once the work has landed. `--safe` requires the same landing proof for a git worktree; discarding work that never landed takes `--discard` with the owner's `--confirm <token>`, never Hydra's. Queued handoff prepares the next branch and transfers its folder automatically. Manual `task attach` retains the worker's branch; the worker prepares a fresh branch before beginning the next task. On a Firstmate-linked Hydra, Firstmate makes and cleans its own copies.


Sharing a folder between Hydras requires an explicit confirmation naming the other Hydras. The CLI returns a token; repeat the attachment with `--confirm <token>`. Settings shows a confirmation dialog with links to those Hydras. Hydra's summary and light check include its projects. On a Firstmate-linked Hydra, the home’s project folders appear read-only and are managed by Firstmate.

## Run

```sh
pnyx-axi serve
```

One server runs every Hydra in the Pnyx data folder (`~/.pnyx`, or `PNYX_HOME`): one port, each Hydra at its own path, http://127.0.0.1:4747/hydra/<id>/, with http://127.0.0.1:4747 opening the default Hydra. Open the `url` it prints; `--port` picks another port, and if that port is taken, `serve` exits with `PORT_IN_USE` rather than picking another. The Hydras list in the left panel switches between Hydras on the same server, and a Hydra created while the server runs is served as soon as its folder appears. A Hydra that fails to load is skipped and reported (in the `serve` output and at `/health`), and the others keep working. Each Hydra keeps its own hook socket, its linked Firstmate home and the agents Pnyx started for it, all inside that one process. `pnyx-axi` with no arguments shows the Hydra summary and the running server's address. Stop a foreground server with Ctrl+C or `pnyx-axi stop`, which stops the server of every Hydra. The login service uses the Node executable and Pnyx installation that ran setup, reaching Node through a link on `PATH` such as `/opt/homebrew/bin/node` when one points to it, so a Homebrew upgrade keeps the service starting; keep that installation in place and rerun setup after moving it or switching Node. The service runs with the `PATH` setup ran with, and on Linux also with `CLAUDE_CONFIG_DIR` and `CODEX_HOME` when they are set, so rerun setup after installing Claude Code, Codex, gh-axi or quota-axi in a new folder. Rerunning setup on a running service replaces it in place: on macOS it waits for launchd to finish stopping the old job before starting the new one, and on Linux systemd restarts the unit with the new configuration. Each Hydra permits one server even when two starts race. A service-managed server restarts after `stop`; use `setup --remove` to keep it stopped.

The browser reconnects automatically with capped backoff and a heartbeat, resumes Hydra events and restores the open conversation subscription. Composers stay usable during an outage; submitting a message keeps its draft and sends it when the connection returns, using the same delivery key on retries. Hydra chat counts a message as sent once its saved event or receipt is confirmed, even while Hydra is still preparing its reply. An uncertain chat or agent-settings save shows a checking state and retries with the same operation ID through reconnects and reloads; a late confirmation clears it. A refused send stays in the chat marked Not sent with the server's reason, and Retry sends it again without making a copy. The pnyx name in the left panel shows an offline mark when the server cannot be reached. Session identities and attachments live in the event log and survive browser reloads and server restarts.

Type `/` anywhere in Hydra’s composer to find skills and commands. Task references after `@`, skills and commands match letters in order anywhere in the name, with gaps allowed, ignoring case, spaces and punctuation: `chatfea` finds “Update the chat comment feature prompt”. Spaced query words match independently in any order, so `feature chat` and `fea chat` find the same card. An unspaced query keeps its letters in order. Matched letters are highlighted. Names starting with the query come first, followed by the tightest matches (fewest gaps, then most matched letters at word starts); ties keep their existing order. For spaced queries, gaps and word-start hits are totaled across the independently matched words. Task prompts and project paths remain searchable after name matches. The picker shares the mention picker’s keyboard controls: typing filters and selects the first result; Tab or Enter inserts it, and Escape closes it. With no matches, Tab also closes it and moves focus normally. A dismissed slash stays closed while you continue typing or move within that query; a new slash, or leaving and returning to the query, starts completion again. Pnyx’s own skills are hidden because they are agent-only instructions. Global skills, the session’s native project skills, readable agent commands and skills from every attached project are grouped by source. Selected skills stay inline as one gold badge, with a leading star, the project’s existing coloured label when applicable, and the full `/skill` name.

The server keeps a metadata index of skill folders, following file changes and checking file stats so edits, replacements and new skills appear on the next menu opening without a page reload. The browser preloads skills when the composer connects and keeps the last list for each Hydra and agent in the tab. Opening the menu shows that list immediately, with no loading indicator, while a background read checks the index; an unchanged result keeps the displayed list in place. Native selections resolve to the receiving harness’s syntax when sent (`/name` for Claude Code, `$name` for Codex). A skill from another attached project sends an explicit instruction to read and follow its `SKILL.md` path; it is never installed or registered with the agent for automatic use.

Replies from Claude Code and Codex agents that Pnyx runs type into Hydra’s chat as they are written: word by word, left to right, at the pace they arrive, catching up within 0.4 s after a pause and finishing within 0.3 s of the reply's end. Half-written formatting such as an unclosed `**` or a table header without its delimiter row waits until it can show whole. Working dots appear as soon as you send, before the server answers. The line beside the dots names what Hydra is doing now and clears when it stops. New messages arrive with a short animation. Reduced-motion preferences turn off the animations, the typing and the scroll glide; text then shows as it arrives, still without half-written formatting. The completed reply stays in the harness’s recorded transcript.

When the server restarts on a new build at the same port, an open Hydra reloads itself and keeps the open card, unsent drafts and scroll position.

To keep it running in the background:

```sh
mkdir -p ~/.pnyx
pnyx-axi setup                             # install the server's login service
pnyx-axi setup --port 4748         # on another port
pnyx-axi setup --preview           # inspect the launchd job or systemd unit
pnyx-axi setup --remove            # stop and uninstall the service
```

On macOS the service is a launchd job in `~/Library/LaunchAgents`. On Linux it is a systemd user unit in `~/.config/systemd/user` (or `$XDG_CONFIG_HOME/systemd/user` when absolute), managed with `systemctl --user`; it runs while you are logged in, and `loginctl enable-linger` keeps it running after you log out.

One login service runs the server of every Hydra, and the server runs every agent Pnyx starts. Setting up the application service replaces the one-per-Hydra services older versions installed for the same data folder.

### Upgrade

`pnyx-axi upgrade`, or `/upgrade` in Hydra's chat, upgrades the Pnyx clone: it pulls `main`, runs `pnpm install` and `pnpm run build`, then restarts the server, and the open page reconnects. It starts at once, while Hydra and the workers keep working. After a passing build the server restarts at the next moment no agent on any Hydra is mid-turn, or after 15 minutes at most; Restart now on the upgrade's row, or `pnyx-axi upgrade --now`, restarts right away. Only the restart stops Hydra: messages sent during it wait in the queued messages and reach Hydra after it. The server restarts only after the build passes; a failed pull, install or build puts the clone back on the commit it started from and leaves the server running. Stop on the upgrade's row, the chat's stop button or `pnyx-axi hydra stop` stops a running upgrade and goes back the same way; Ctrl-C does it for `pnyx-axi upgrade`. The few seconds of the restart itself cannot be stopped. A clone on another branch or with local changes is refused with every reason, and nothing is stashed. A failed or refused upgrade in the chat offers Ask Hydra to fix, which drafts a prompt for Hydra in the composer. The restart stops the agents the server runs, including Hydra and its routine helper; a turn the restart cut resumes from its saved session when the server is back.

Once a day the server asks the clone's `origin` (`git ls-remote`, no login) whether `main` has a newer commit, and an "Upgrade available" hint then appears next to the pnyx brand. An offline check keeps the last answer, and nothing shows until a check has answered. `pnyx-axi upgrade --check` asks the same question, and `pnyx-axi --version` shows the installed commit. Upgrading is never automatic: Hydra can only propose `pnyx-axi upgrade`, and workers cannot run it.

### Named links with portless

[portless](https://github.com/vercel-labs/portless) gives local servers stable HTTPS names such as https://pnyx.localhost instead of port numbers. The server accepts any `*.localhost` host and origin: browsers resolve those names to this machine themselves, so another site cannot rebind them. Set it up once (it asks for your password once):

```sh
npm install -g portless
portless trust && portless service install   # trust its certificate, run its proxy on port 443 at login
portless alias pnyx 4747                      # https://pnyx.localhost for the login service
```

Start a preview server under a name of its own, so its link is https://<name>.pnyx.localhost. `serve` takes the port portless hands it in `PORT` when `--port` is not given, and a data folder of its own keeps it apart from the login service's Hydras:

```sh
PNYX_HOME=<dir> portless <name>.pnyx pnyx-axi serve
```

## Task records

Hydra can be Firstmate or an ordinary agent session. Each Hydra has one orchestrator identity, and each explicit task has zero or one attached worker. Tasks support one level of subtasks. Pnyx records work and queues messages; Hydra decides what to do and dispatches workers. Changing Hydra preserves tasks, earlier worker attachments and messages to previous Hydras.

Use `hydra create|set|show|list` for Hydras, `column create|rename|describe|rule|resize|delete|reorder|list` for their columns, and `task create|brief|hide|unhide|hide-after|rename|status|ask|answer|escalate|list|show|history|chat|move` for work records. `task create --parent <task>` creates a subtask. `task create --before <task>` places the new task before an existing task in the same destination column in its creation event; the browser uses it to place new tasks at the top. Creating a task in a role column records that role's initial status. Pnyx moves a card on an explicit lifecycle change (see Columns), the owner arranges the rest, and Hydra uses manual placement only for owner requests or exceptional corrections; `move <task> <column> [--before <task>]` (or dragging the card) places it by hand. `column delete <id> --to <column>` moves every task in the deleted column to `--to` (the first remaining column by default), and Undo refuses to overwrite later edits. The final column cannot be deleted. CLI card moves, column rule edits, column reorders and column deletes first return `confirmation: needed` with a token and a summary; repeat the exact command with `--confirm <token>` to act. A changed target invalidates the token. Browser gestures act directly on the owner’s instruction. Hydra’s own changes (writes with actor `hydra`) through `move`, `task create|brief|hide|unhide` and `task start` must carry one short `--reason "<why>"`. Pnyx stores the reason on the event and shows the change in the task’s Updates. Changes made during your turn fold under Hydra’s reply, grouped by task. The owner’s own moves and edits need no reason.

Create a task with `task create --title "<title>" --ask "<owner words>" --intent "<the owner's goal>" --brief "<build instructions>"` and edit its brief with `task brief <task> --brief "<instructions>"` (empty text clears it). `--intent` is the card's Intent: what the owner wants from the task and why, which Hydra writes as it creates the task, in 1 to 4000 characters. When the goal itself changes, Hydra rewrites the whole Intent with `task brief <task> --intent "<new Intent>" --reason "<what changed>"`, with or without a new `--brief`; the card shows the newest Intent and the task's history keeps the earlier ones. Starts include the brief in the opening prompt, whether Pnyx runs the agent or it starts through Paseo, Firstmate or the configured command. An explicit `task attach` sends it through the attached agent’s reply route once per attachment; the attachment receipt includes its delivery result. `task hide <task>` removes work from the live Hydra and `task unhide <task>` restores it; both are events and preserve all history.

The owner's ask is append-only and appears before Hydra's build instructions in worker prompts. `task owner-ask <task> --text "<owner words>"` adds a later ask with its time (the old `task intent` refuses and points to it); messages sent directly on the task are added automatically. Hydra must supply `--message <saved-owner-message-id>` when quoting the owner at intake or adding an ask, and Pnyx checks the exact quote. Rewriting the brief never changes the ask. Workers account for each part of the ask in their completion note.

Move a task to another Hydra with `task move <task> --to-hydra <hydra> [--reason "<why>"]`; Hydra must give the reason, the owner need not. The card arrives with the same id and key, its chat (messages logged on the earlier Hydra included), its title, Intent, brief, owner asks, questions and answers, links, project label, status and worker sessions, in the target's column with the same id, even when its title differs; else the one with the same title; else where the target's column rules place it; else the target's parked column, or its first. The source Hydra stops listing it, and a command there that names the task says which Hydra it moved to. Each Hydra logs one event with the same id, `task.moved-out` on the source and `task.moved-in` on the target, and neither log is rewritten. If a crash cuts a move between the two lines, running the same `task move` again finishes it, carrying any source edits made since; when the target's copy was also edited, it refuses and names the commands to compare both copies and hide one. `task history` on the target continues into the earlier Hydras' events, with a `hydra` column, and `--before <hydra>:<seq>` pages through them. A Pnyx-run worker between turns comes along: the source records its transcript up to the move and ends its idle session, and its next turn resumes the same session under the target, with that Hydra in its environment, which reads the transcript on from there. The card's notes and its owner questions' reminder times come along too. The task copy stays where it is, because the worker's transcript belongs to that folder; the source Hydra never hands it to another task. Pnyx refuses the move, naming the command that clears it, while the target lacks the task's project (`project add <path> --hydra <target>`), its worker is starting, mid-turn or runs outside Pnyx (`task detach`), the routine helper holds it, it is queued or has tasks queued behind its worker (`task unqueue`), it has prerequisites or dependents (`task undepend`), it waits on a task or another waits on it (`task status <task> paused --hold`), it is a subtask or has subtasks, an external source still runs for it (`task source stop`), it mirrors Firstmate, or the target follows a Firstmate home. `undo` refuses a move and prints the move back, which is the same command.

Hover the agent icon on a card to see its model, settings, session details and recorded task tokens. `task show` includes the same token totals, from supported worker transcripts and Hydra turns that explicitly name the task. Worker handoffs keep earlier usage on the earlier task. Missing transcripts and unattributed Hydra turns are excluded from recorded totals. The same usage panel in the card and composer shows current context separately: used and remaining tokens, a bar that turns amber at 70% and red at 90%, and the provider that reported the count. Session cost takes priority over context tokens; unknown context reads “Usage unavailable.” Plan limits include a known plan badge and reset dates. The refresh button refreshes plan limits only. Shared Hydra turns are identified in the usage explanation.


Set a reminder by telling Hydra “remind me about this tomorrow” or using a card’s hover pill → Remind. The CLI is `pnyx-axi task remind <task> "tomorrow 9:00" --hydra <id>`; it also accepts `"in 2 hours"` or a future ISO timestamp with a timezone. “Tomorrow” uses the laptop’s timezone and defaults to 9:00. Each task has one reminder: setting another replaces it, and `task remind <task> clear` clears it. Waiting reminders appear on cards; `task reminders` returns their list and count, including each repeat policy and next occurrence.

For recurring follow-ups, add `--every "4 hours" --until worker-started|question-answered|task-done`. Intervals accept positive whole minutes, hours or days. `question-answered` also takes `--question <id>` for an open owner question and stops when it is answered or closed. `worker-started` stops on the next recorded worker launch, assignment or working declaration. `task-done` requires unfinished work and stops on recorded completion. The reducer checks these conditions as events arrive, so cancellation persists across restart and needs no agent turn. After a missed interval, the server posts once and advances to the next future occurrence instead of replaying every missed nudge. Card date edits keep the existing repeat policy; Clear removes it.

When reminders fall due, the server records each task’s receipt, moves its card to Needs you (restoring that column if needed), and brings hidden work back. Scheduled reminders and overdue owner questions due in the same sweep appear in one automatic Pnyx message. Questions use one grouped line, “N questions waiting on you: [card] · [card]”, with each task linked once; scheduled reminders keep their own short lines. Task links open the full title and question. The batch and question reminder clocks are saved together, so restart does not duplicate a delivered batch. Owner questions keep their four-hour cadence and can post while Hydra is working; setting `--review-minutes 0` disables automatic question reminders. Posting reminders starts no agent, and Hydra does not restate them in its replies. On an externally linked Hydra, an unchanged record leaves a due reminder in Needs you; clearing the reminder or a newer source record resumes source placement.

Columns carry an executable placement rule and a description, available through `column list` and set with `column create --description "<when and why>"` or `column describe <id> --description "<when and why>"`. `column rule <id> --when "<fact>[,<fact>]" --reason "<why>"` replaces a rule after confirmation. Commas mean AND, repeated `--when` options mean OR, and `!fact` means NOT; the first matching column in display order wins. `column rule <id> --clear --reason "<why>"` makes it manual only. Rules use worker state (`worker:none|working|checks|blocked|hydra|paused|ended`), `owner-question`, `held`, pull request state and checks (`pr:none|draft|open|pending|green|red|merged|closed`), `kind:build|investigation`, `done`, `reminder-due`, and `queued` behind a worker. A custom Research column before In progress can use `--when "kind:investigation,!done,!held,!owner-question,!reminder-due"`. New custom columns start manual only. The digest lists column names, task counts and descriptions; `column list` also prints every placement rule. `column resize <id> --width <pixels>` and `hydra resize --width <pixels>` persist widths. `layout show` reports overrides and stored defaults (460 pixels per column, 520 for Hydra); `layout reset` restores those widths while preserving other preferences.

### Atomic local changes

Use one apply document when related task changes must succeed together:

```sh
pnyx-axi apply --file changes.json --check --hydra work
pnyx-axi apply --file changes.json --event-id export-plan-1 --hydra work
pnyx-axi apply --file - --check --hydra work < changes.json
```

```json
{
  "version": 1,
  "expected": {"tasks": {"existing-task-id-or-key": 7}},
  "changes": [
    {"op": "task.create", "as": "research", "title": "Research export", "kind": "investigation", "reason": "Compare the formats before building"},
    {"op": "task.brief", "task": "existing-task-id-or-key", "brief": "Use the research findings", "reason": "Keep the instructions current"},
    {"op": "task.depend", "task": "existing-task-id-or-key", "on": ["$research"]}
  ]
}
```

Duplicate JSON member names, including escaped spellings of the same name, are refused with their field paths before schema validation. The top-level fields are exactly `version` (currently `1`), optional `expected` and a nonempty `changes` array. `expected` contains only `tasks`, a map from existing task IDs or keys to their expected non-negative integer revisions. These revisions refer to the state before the document; several changes to the same task need only one entry. Unrelated events do not conflict. Applying revalidates against current state at write time.

Every operation accepts an optional nonempty `reason`. Required fields appear in bold below. Text fields are strings; brief and note may be empty. `task`, `parent` and each `on` reference name an existing task ID/key in this Hydra, or `$alias` from an earlier successful create in this document. `as` must be unique and match `[a-zA-Z][a-zA-Z0-9_-]*`. Forward aliases are refused.

| `op` | Fields besides `op` and `reason` |
| --- | --- |
| `task.create` | **`title`**, optional `as`, `key`, `project`, `intent`, `brief`, `folder`, `kind` (`build` or `investigation`), `hold` (boolean), `parent`, `column`, `before`, `ask`, `message` |
| `task.brief` | **`task`**, at least one of `brief` (empty clears it) or `intent` (1 to 4000 characters); both may be supplied |
| `task.owner-ask` | **`task`**, **`text`**, optional `message` (saved owner-message ID) |
| `task.depend`, `task.undepend` | **`task`**, **`on`** (nonempty array of task references) |
| `task.status` | **`task`**, **`status`** (`working`, `needs_you`, `paused`, `blocked`, `done`), optional `note`, `until` (ISO time or relative time), `hold` (boolean) |
| `task.hold` | **`task`**; `reason` is required |
| `task.release` | **`task`**, **`message`** (owner message newer than the hold); `reason` is required |
| `link` | **`task`**, **`url`** (HTTP/S), optional `kind` (`github_pr`, `linear`, `url`), `number` (digit string), `title`, `state` (`open`, `merged`, `closed`), `remove` (boolean) |
| `outcome` | **`task`**, either `state` (`done`, `failed`, `cancelled`) or `clear: true`; optional `note` when setting a state |

The `intent` field is the card's goal; `task.owner-ask` saves exact owner words separately. There is no `task.intent` operation. Create has the same project, parent, column and owner-ask validation as `task create`. `message` on create requires `ask`. Hydra must give a reason for creates, brief/Intent edits and owner asks, and quote saved owner messages exactly for owner asks. Discussion holds and prerequisites remain owner/Hydra operations. A release requires the owner's newer saved message. Status `until` and `hold` apply only to `paused` and cannot be combined. Done declarations retain report-review and landing gates and are checked again against the resulting document. A recorded outcome remains distinct from proof that work landed. Removing a link cannot also change its metadata; clearing an outcome cannot also set its note. Unknown or meaningless fields are refused.

`--check` returns `applied: false`, `check: true`, resolved aliases, watched `base` revisions, resulting `revisions`, per-operation results and a `diff` of changed fields with bounded text and collection summaries. Add `--full` to preview complete records; an already-recorded event ID refuses a full preview and points to history. It does no maintenance, creates no Hydra folders and writes no log or snapshot. Generated task IDs in a preview are provisional unless the same `--event-id` is supplied when checking and applying. A preview grants no approval and applying rechecks the complete document. Validation errors exit 2 with `applied: false` and an `errors` table containing zero-based `operation`, JSON-pointer `path`, `code` and `reason`; independent errors are collected. File/JSON errors use `/file`.

A successful apply returns `applied: true` and appends one `log.transaction` record containing every event, including automatic declarations, question reconciliation and lifecycle moves. The reader exposes the ordinary child events to history, subscriptions and deterministic replay. A torn record exposes none of its events; `repair` preserves and skips the incomplete tail, as for a torn ordinary event. Snapshots remain derived. All requested changes and their receipt become durable together. This log format requires a version of Pnyx that supports apply.

Keep one `--event-id` and the same document when retrying an uncertain apply. A mutating retry returns the receipt the server already recorded. An identical retry returns the original aliases and resulting revisions with `duplicate: true`, even after later edits. Reusing the ID with different document contents or actor returns `IDEMPOTENCY_CONFLICT`. The event IDs under `<event-id>:op:<index>` and their colon-delimited descendants are reserved for that operation; an existing ID anywhere in that namespace refuses the document. Even an unchanged document retains its retry identity. Correct mistakes with a new apply document: `undo` refuses individual events belonging to a transaction, and there is no whole-batch undo.

This command covers one Hydra's local task events only. Worker starts/messages, queues, memory, columns, view/layout, Hydra/project settings, dispatch rules, merges and other external effects are unsupported and fail before writing. Short commands for the covered changes use the same planners. Scalar flags cannot repeat, and these task commands reject irrelevant flags: for example `task rename --brief` and `task create --on` fail instead of reporting an incomplete success. Use `task brief` or apply to change a brief.

## Memory

Owner memory is Pnyx-wide: every Hydra's full digest prints it. It holds the owner's preferences under the key `preferences` and general learnings under `learnings`, through `owner memory list`, `owner memory set --key <short-name> --text "<document>"` and `owner memory forget --key <short-name>`, within 24000 characters. It lives in `$PNYX_HOME/owner/memory.jsonl` (by default `~/.pnyx/owner/`), an append-only log that keeps every replacement and removal. Saves take `--if-revision <n>` from `owner memory list`, so a save made from an older read is refused rather than replacing another Hydra's save. The first run of this version moves each Hydra's `preferences` and `learnings` there, merging lines that repeat, and forgets them in the Hydra, whose event log keeps the old text; a Hydra that cannot be moved keeps them in its digest and the next read retries.

### Worker instructions and memory curation

Hydra reports results in plain words with full links and what happens next, in one message per result. Routine progress, checks still running and re-runs stay on the cards, questions stay on their question cards, and the Waiting on you bar shows what waits on you. Owner messages always call for an answer; if a hosted Hydra ends one with `NO_REPLY`, Pnyx asks once for a standalone reply.

Standing worker instructions reach every new worker header, after its fixed scope and authority lines: Hydra-wide notes first, then project notes, both verbatim and deferring to those fixed rules. Read them with `hydra memory list` or `project show <name>`. Save the whole document with `pnyx-axi hydra worker-notes set --text "<instructions>" --reason "<why>" --hydra <id>` or `pnyx-axi project worker-notes set --project <name> --text "<instructions>" --reason "<why>" --hydra <id>`; `forget` clears it. Each document is limited to 1500 characters within its memory layer's budget. Every edit is recorded and posts a line as Pnyx in the editing Hydra's chat. When workers repeatedly stop on something your standing preferences settle, Hydra answers the worker and adds a short rule here so future workers have it too.

Each owner or project learning line keeps its own last-confirmed time and unused-save count. Normal learnings become stale after 30 days or 10 unused memory saves, whichever comes first. Add short-lived “for now” lines with `memory set --key learnings --text "<whole document>" --kind for-now --until <condition>`; the flags apply to new lines only. These become stale after 7 days or 3 unused saves and must name `task:<hydra>/<task-key-or-id>`, a full PR URL, `version:<version>`, or `date:YYYY-MM-DD`. Dates expire at midnight UTC. Task completion and followed PR merges are checked from saved Pnyx state; versions and unavailable task or PR state need Hydra's evidence. Digests and timed reviews surface stale and expired lines without changing memory.

Finish an inscribe pass with `owner memory save --reason "<what you checked>"` or `project memory save --project <project> --reason "<what you checked>"`. Each advances only that layer's unused counts. Add `--used "<exact line>"` (newline-separated for several) with session evidence in the reason to refresh their dates and clear their counts instead. Reads, document edits, wakes and timed reviews never advance counts. Reconfirm a line with `owner memory confirm --text "<line>" --reason "<session evidence>"`, or the project equivalent. Recheck stale lines, then confirm or use `memory archive --text "<line>" --reason "<why>"`. `memory list` shows each line removed by an archive, set or forget, with the date and reason of that change; restore one with a new set. Lines dropped by a profile refresh or moved to a project are not listed. Old logs need no rewrite: missing kind and count mean normal and zero. Preferences stay undated and never decay.

Hydra memory holds only what one Hydra needs, such as its `scope`, where it left off (`left-off`), and its `check-cursor`, through `hydra memory list`, `hydra memory set --key <short-name> --text "<fact and why>"` and `hydra memory forget --key <short-name>`, within 1500 characters. Entries replace by key, survive a Hydra switch and remain isolated to their Hydra; all replacements and removals stay in the event log. The timed review flags a `left-off` once every task it links as `[@Title](pnyx-task:<id>)` is done, or once it is 7 days old. In both layers a save that would exceed the budget is refused, and the digest asks Hydra to curate a nearly-full memory. Before a context reset Hydra runs the `inscribe` skill, Pnyx's take on Firstmate's `/stow`: it routes each fact to owner, project or Hydra memory and saves the documents it changed.

Project memory is shared by every Hydra that attaches the same normalized git remote, including different clones and worktrees. Repositories without a remote use their canonical path. It lives under `$PNYX_HOME/projects/<id>/events.jsonl` (by default `~/.pnyx/projects/<id>/`), separately from Hydra state. The `profile`, `preferences` and `learnings` documents share one 10000-character budget; over-budget saves are refused and the digest nudges Hydra to curate nearly-full memory. Project preferences stay until changed. General owner preferences belong in owner memory.

Hydra writes the first profile from the project's default-branch AGENTS.md, CLAUDE.md, README and skills: build/test/lint commands, PR rules, key skills and when to use each, and main conventions. Pnyx hashes those sources without model calls and marks the profile out of date when they change. It reads locally available default-branch refs without fetching; changes must reach that ref to invalidate a profile. With no git repository, it hashes the attached folder's sources. A repository whose default branch is unavailable cannot acknowledge a profile refresh. The next Hydra reads only changed sources and replaces the profile; preferences and learnings remain. The digest lists attached projects in a one-line index with profile freshness; Hydra loads a project's memory on demand with `project show <name|path>`. Workers receive a short version for their assigned project.

Curate through chat or `/inscribe <project>`. `pnyx-axi project memory list --project <name|path> --hydra <hydra>` prints documents, usage, source hashes, changed files, the source ref and its fingerprint. Read files with `git -C <project> show <ref>:<file>`; then save a profile with `project memory set --project <name|path> --key profile --text "<profile>" --sources <fingerprint> --reason "<why>"`. Use the same command with `--key preferences` or `--key learnings` without `--sources`, or `project memory forget --project <name|path> --key <key>`. Writes support `--event-id` and `--if-revision` using the project memory revision. Replacements and removals stay in the append-only project log. Move one owner learning with `owner memory move --project <name|path> --text "<exact learning line>" --if-revision <owner revision> --hydra <hydra>`. One durable entry in the owner log records the removal and project addition together; project replay includes these moves in sequence with its own events. The move preserves the learning metadata, refuses growth over the project budget and leaves both memories untouched on refusal. When owner memory is nearly full, inscribe moves clearly project-specific learnings itself; moving owner preferences requires an answered owner question. Hydra names applicable project skills in each task brief, and the standard worker header tells workers to read their current copy's AGENTS.md and CLAUDE.md plus the relevant skills, docs and context files they point to.

A Hydra that Pnyx runs works from `~/.pnyx/hydras/<hydra>/agent/`. Before each Hydra turn Pnyx writes its contract there as `AGENTS.md`, with a one-line `CLAUDE.md` importing it, so Claude Code and Codex load Hydra's whole job every turn, plus the detail skills the contract tells it when to load. If a shipped skill is missing, Pnyx logs its path and continues with the available skills; `/upgrade` repairs the install. Pnyx gives Hydra a full digest of its live state, owner memory and Hydra memory when a session opens and after compaction, plus a compact attached-project index. Wakes into a running session carry the change/check prompt, the open decisions and a one-line note when memory changed; `pnyx-axi hydra digest` prints the same digest for a Hydra run anywhere else. Every worker a Hydra starts opens with one generated header that states its task, that it stays in its own copy, runs routine commands without asking, escalates only real decisions to Hydra, and where it stops: its project's landing rule, or an investigation's stored report.

### Pending owner questions

An owner question stays open until answered or its work is explicitly finished or cancelled. A worker session ending, a completed investigation, or a related pull request merging does not settle an unrelated decision. A merge question closes when its own pull request merges or closes. Report-origin questions and the current bound Go hold retain their existing gates. Unresolved owner questions prevent automatic removal of their cards; finished cards otherwise keep the usual 24-hour retention.

Use `task discuss-question <task> <question> --text "<clarification>"` to discuss a question without answering it. Short requests such as “why?” or “explain”, and recognized clarification questions ending in “?”, also send discussion through `task answer --text` and keep the question open. Longer instructions such as “Why not both? Ship A first.” remain answers; use `discuss-question` for other follow-up wording. Hydra cannot record that clarification as an owner answer with `--from-message`.

Use `task defer-question <task> <question> --until "<future time>"` for Later. It accepts the same times as task reminders, including an ISO timestamp with a timezone. The question leaves active Waiting on you and its automatic and question-linked repeating reminders pause. The saved question and authorization gate remain unresolved, including after restart. At the requested date the server makes it active again, even with automatic reminders disabled. Use `--until clear` to bring it back early. Undoing an answer preserves a future Later date and clears an expired deferral immediately. Hydra may record a deferral only with `--from-message <owner-message>` naming the owner’s own newer instruction; workers cannot defer it.

A pull request has one canonical review approval within a Hydra, even when several tasks link it. For a ready pull request, linked cards show Ready for review with Review, Merge and Hold controls for that same approval. A pending approval remains answerable on its card if the link is removed or returns to draft. Merge records approval for that exact URL; Hydra still checks authorization, checks and the verified head before merging. Hold can later be changed to Merge by the owner, or by Hydra quoting the owner’s newer explicit instruction. Hydra-merge projects keep their existing authority and checks.

Task questions live on their cards with Needs you and Waiting on you. Chat shows a task question only for a blocker, labelled Blocker with its card link, or while the owner explicitly selects or mentions the task. Matching a title in ordinary prose does not select a task. Hydra-wide questions use `hydra ask --question "<question>" [--context "<context>"] [--choice "<label>"]` and live in chat. Later is available on the question; a deferred Hydra-wide question keeps its date controls in chat. Follow-up discussion leaves the question open. Recorded answers can be reviewed and undone on their task card, or in chat for a Hydra-wide question. Hydra announces its own decisions in one chat line linked to the card, rather than asking the owner to approve a choice their words already settle.

### Status and retained history

A task's recorded status is an explicit declaration or a successful task/agent operation's lifecycle fact (working, needs_you, paused, blocked or done). Its lifecycle places the card: see Columns. The app's badge is computed separately from observed questions, native work, checks and queues; declarations remain worker notes. Pnyx declares a task done itself only once every non-abandoned linked pull request has merged. Silence, finished turns and session exit do not complete tasks. Firstmate's backlog, status text and worker metadata are mirrored into retained task records, including backlog items without workers. A Hydra stops mirroring a home when that home no longer runs it.

The append-only log preserves Hydra, task, subtask, session, command and message identities. Replaying existing events migrates old session records without changing their event bytes or ids. Unattached and headless sessions remain available through CLI history and search. Harvested user and assistant messages are redacted and copied into the log on turn end, attachment changes and explicit `harvest`, so observed conversations remain readable and searchable after a native transcript disappears. Oracle remains a derived, deletable index. It searches saved task briefs, intents, owner asks and investigation reports, including earlier versions, and helper results associated with their tasks. Use `task report <task>` for the latest stored report. Unchanged helper waits are omitted.

`hydra send --text <message>` queues a Hydra-level message with no task, and `hydra stop` ends the turn Pnyx's hosted Hydra is running without touching its workers. `hydra send --task <task> [--action send|worker]` queues a task-specific message, which the chat opens with the task's chip unless its text already mentions the task, and `hydra messages` reads the queue. These actions never launch a worker; starting one is `task start` (below). A worker's own message (actor `worker:<task>`) reaches Hydra wrapped as a `<pnyx-report>` with its origin and stays out of the owner's chat; Hydra tells the owner what it decided. Hydra’s own messages (actor `hydra`), including the lines Pnyx posts for its changes, appear in the chat as Hydra’s and stay readable through `hydra messages`, task history and `hydra check`, which lists them without waking on them. Several workers per task and automatically generated labels are later work.

`hydra message` looks up the recorded Hydra chat; `task messages <task>` uses the same options for a task's thread, including its past agents. Use one selector: `--id <message-id>`, `--seq <event-seq>` or `--at <ISO-time-with-timezone>`. A selector alone returns exactly one whole message. Add `--before <n> --after <n>` for surrounding messages, or `--budget <tokens>` to grow around it to the page limit. Explicit before/after counts override that side of a budget window. IDs and event sequences stay usable after inscribe, compaction and agent replacement. Lookup also accepts the event ID or sequence of any transport chunk and rejoins the whole message before selecting or counting it.

```sh
pnyx-axi hydra message --seq 42 --before 3 --after 3 --hydra sample
pnyx-axi hydra message --at '2026-01-01T10:00:00.000Z' --budget 2000 --hydra sample
pnyx-axi task messages <task> --id '<message-id>' --before 2 --after 2 --hydra sample
pnyx-axi hydra message --seq 42 --direction older --limit 10 --hydra sample
pnyx-axi hydra message --from 30 --to 60 --hydra sample
pnyx-axi hydra message --cursor '<older-or-newer-cursor>' --hydra sample
```

`--direction older|newer` pages before or after a selected message, excluding that message. With no selector it starts at the corresponding end of the conversation; the default is the oldest page. `--from` and `--to` accept sequences or timezone-qualified ISO times and include both endpoints. Results always appear in chronological order, including delayed transcript harvests whose sequence order differs. `older` and `newer` cursors preserve the Hydra, thread, inclusive range and log snapshot, so later messages cannot shift a continuation. Pass only `--budget` or `--limit` alongside `--cursor`; start a new selection to include newly recorded messages. A timestamp shared by several messages returns a conflict with candidate references instead of choosing one.

Pages default to 20 messages and at most 6,000 estimated tokens, with a hard limit of 60 messages and 20,000 JSON bytes for their records. Lower `--budget` and `--limit` to read less. Messages stay whole; a single message that exceeds the requested budget or hard byte cap returns `MESSAGE_TOO_LARGE`. The byte cap includes JSON escaping. Native transcript messages are harvested into the durable log before lookup; an unavailable native transcript still leaves its previously harvested messages readable.

### Steering inbox and external sources

Native tasks have an event-backed steering inbox. Enqueue with `pnyx-axi task inbox enqueue <task> <message-id> --text "<instruction>"` (or `--file <path|->`). Inbox writes use message and attempt IDs for retries and reject `--event-id` and `--if-revision`. A message ID identifies one instruction: retrying it preserves its number, and the same text with a new ID creates another instruction. `--source` and `--reply` retain its origin and reply correlation.

Workers run `pnyx-axi task inbox read <task>` to read pending instructions in order and obtain the current session/generation claim. An authenticated worker read persists read acknowledgements for the returned instructions, stopping reminders immediately. A new instruction to a worker Pnyx runs arrives in its input with its text and counts as read once the agent takes it; a repeat names only its ID. Owner and Hydra inspection is read-only. An acknowledgement means read, never completed work; workers report progress and blockers with `task status` and file questions with `task ask`. `task inbox ack <task> <message-id> --session <session> --generation <number>` explicitly records the same receipt and is idempotent for that claim. The default outcome is `read`; legacy `incorporated` and `blocked` outcomes remain accepted and replayable. `read --all` includes acknowledged history for recovery after an interruption. Detaching or replacing a worker invalidates its old claim while preserving unread instructions.

`task inbox notify <task> <message-id> --session <session> --generation <number> --attempt <attempt-id> --result delivered|unknown|failed|deferred` records a notification attempt separately from reading. The inbox is rebuilt from the append-only event log through the normal snapshot projection. Existing reply receipts retain their delivery meaning; ordinary replies to native tasks persist their full payload in this inbox before notifying a hosted Claude/Codex worker, a Paseo agent or a terminal worker. Their reply ID is the message ID, and the runtime receives a short notice naming pending IDs. Opening or resuming a hosted worker replays unacknowledged IDs in order, even when an earlier notification was delivered. A held worker stays held. Controls, permission answers and question answers retain their dedicated delivery paths. Workers checkpoint effects and consult acknowledged history after a crash so recovery can verify work already performed. The server follows the oldest unread instruction even after a delivered transport receipt: after 90 seconds it allows at most three scheduled notification attempts. A working worker keeps its pending instruction without spending that budget or waking Hydra. Busy deferrals keep the 90-second pause and do not spend the retry budget, including when the worker becomes busy during notification. Other deferrals retain their separate limit of two attempts. For terminal workers with a recorded process ID, a process check runs before suppressing busy recovery; confirmed process exit still reports an unread instruction even if a missing stop hook left the worker or its children marked working. Attempts are reserved durably before sending, so a crash or reassignment cannot reset that budget. Exhaustion records one actionable “instruction unread” result for Hydra in the same event that wakes it; the instruction stays pending until read or explicitly acknowledged. A worker read acknowledges the returned pending instructions and lets later instructions advance. Restart/resume reconciliation retains the same IDs and is separate from the scheduled budget. A hold never resumes its worker. Terminal notices require a verified empty Claude Code/Codex composer in tmux; drafts and permission prompts defer them, and terminals without a safe composer inspection report uncertainty without typing. Paseo agent notices use its message API without changing a UI draft. Legacy unconfirmed receipts retain transcript-based uncertainty checks. Firstmate-owned tasks keep Firstmate's inbox.

Native tasks can register external jobs or listeners for the existing server to supervise outside agent turns:

```sh
pnyx-axi task source register <task> job --executable /absolute/path/to/tool --argv '["listen","job-id"]' --cwd /absolute/project --hydra work
pnyx-axi task source list <task> --hydra work
pnyx-axi task source read <task> job --hydra work
pnyx-axi task inbox ack <task> <result-message-id> --session <session> --generation <number> --hydra work
pnyx-axi task source handled <task> job <sequence> --session <session> --generation <number> --hydra work
pnyx-axi task source stop <task> job --hydra work
```

Registration binds an assigned worker's session/generation, the executable's real path and SHA-256, exact argv and working folder. Arguments are passed directly without a shell. Register only a trusted command; files named in argv remain that command's responsibility. The same source ID and configuration is idempotent; choose a new ID for changed configuration or a replacement worker. Completed output first enters a private capture buffer, then becomes an event before its stable inbox message is queued or a notification is sent. The buffer survives a writer failure or server restart and is removed after the event is flushed. A process exit or successful notification leaves its result unread. A worker read acknowledges receipt of the inbox message, then the current worker explicitly marks the result handled when fully resolved; terminal handling retires the source. `read --all` includes handled results.

The default limits are one hour, 64 KiB combined stdout/stderr and a one-day registration expiry. Set `--timeout-ms` (up to one day), `--max-bytes` (up to 1 MiB), or `--expires <ISO-time>` explicitly. `--restart on-failure --max-runs <1–10>` allows another confirmed failed run only after its result is handled; the run count survives server restarts. Successful, stopped, expired, oversized, interrupted and stale-owner results are terminal. An interrupted listener has an uncertain external outcome: verify the external job before registering another source. The server never guesses that rerunning an interrupted command is safe.

The server owns one listener per registration. Its child supervisor stops the source's process group when the server connection closes. Restart replays unread results and records a lost listener as interrupted. Holds retain captures and queue their inbox messages without resuming the worker; expired registrations and replaced workers cannot launch old commands. Failure, uncertainty, hidden or held results, and acknowledged results left unfinished after a worker turn create one durable Hydra alert per result. These alerts can start Hydra even before its first chat message. Hidden results remain readable and enter the task inbox when the task returns. Firstmate-owned tasks continue using Firstmate's external-source lifecycle.

### Lavish feedback

Workers can put an already-open Lavish page on the same durable transport:

```sh
pnyx-axi task source lavish <task> page-1 --page .lavish/review.html --executable "$(command -v lavish-axi)" --hydra work
pnyx-axi task source read <task> page-1 --hydra work
pnyx-axi task source lavish <task> page-2 --page .lavish/review.html --executable "$(command -v lavish-axi)" --after page-1 --sequence 1 --session <session> --generation <number> --agent-reply-file reply.md --hydra work
```

The worker owns the page and its feedback; Hydra relays its link. A registration binds the canonical page, worker claim, exact predecessor round and optional reply text/identity. The server posts a staged reply once through `lavish-axi reply`, saves its acceptance receipt, then launches `poll`. Registration alone does not mean listening: inspect the source's running state and reply acceptance first. A failed or interrupted post remains an unread result and never starts a poll. Repeating the same registration preserves its identity; a round cannot acquire a second successor. Inbox read acknowledges receipt. Apply and checkpoint all feedback before re-arming; re-arm handles that exact round and registers its successor together. Real owner choices use `task ask` and the existing report-review inventory.

An empty End or feedback with `session_ended` remains owed until handled, then retires; re-arm is refused. Unknown responses and disconnected sessions also stop for worker attention. Polls use the existing one-day limit and capture bounds. A server restart preserves registrations, receipts and unread rounds. A lost running poll produces an interrupted result; the worker checks the uncertainty and explicitly re-arms instead of blindly replaying a destructive read. Expired, stale-assignment and explicitly stopped registrations can also be recovered by the current worker after acknowledgement; none restarts automatically. Lavish consumes feedback when returning it, so output lost before reaching the source supervisor cannot be recovered by Pnyx. Reply acceptance has no remote idempotency key: an uncertain post requires inspection before another explicit publication.

## Starting workers and Hydra

Hold an idea for discussion with `pnyx-axi task create --title "Idea" --hold` or `task hold <task> --reason "Discuss first"`. It stays in Backlog marked **Talking** and cannot start, build, queue or continue. Once Hydra has played back its understanding, it asks `task ask <task> --to owner --kind go --question "Ready to build?"`; the card moves to Needs you. Answering **Go** releases the hold and closes the question together. **Hold** keeps the discussion held. Hydra can also release with `task release <task> --from-message <owner-message-id> --reason "Owner approved"`, quoting an owner message newer than the hold. If an open go question is bound to that hold, release records its Go answer and source in the same event; the source must also be newer than the question. Other questions stay open.

`pnyx-axi task start <task> --via pnyx|paseo|firstmate|command` starts one worker for a task and attaches it; `pnyx-axi hydra start --via paseo|firstmate|command` starts the Hydra. Pnyx runs the agents it is asked to start; Hydra still decides what to do. Pnyx records each start on the Hydra.

- **Pnyx (the default):** `task start <task> [--rule <name>] [--harness claude|codex] [--account <name>] [--prompt "..."] [--folder <path>]` has the Hydra’s server (`pnyx-axi serve`) run Claude Code through the Agent SDK or Codex through `codex app-server` in the task's folder, with the brief as its first prompt.
It records the native session or thread id, folder and settings on the task and loads your own provider configuration, skills and hooks. Install the chosen provider's CLI and sign in before starting. Hooks report to the same task. The chip reads **Claude Code · Pnyx** or **Codex · Pnyx**; `pnyx-axi reply` and model, effort and mode changes through `pnyx-axi agent` go straight to it, and working or finished comes from the agent itself. Codex applies picker changes on its next turn. A message sent during a turn joins it, as with Claude Code (Codex takes it through `turn/steer`); one sent while a turn is being stopped starts the next turn instead. Stopping the server stops its agents: after a restart each task still shows its agent, and the provider's conversation remains available through CLI history, a running turn is marked interrupted and waits for you or Hydra, and the next message resumes the same session or thread. Tool permission requests appear inline with **Allow / Deny** and a **Needs you · permission** marker; the card stays in its column. Hydra sees them through `hydra check` and can answer with `pnyx-axi task permission <task> <request> allow|deny --actor hydra --reason "<why>"`; its reason appears in Hydra’s chat. Your own permission rules run first, so tools they already allow never ask in the Hydra. The first answer wins and does not change your permission rules. Command and file approvals apply once; Codex turn-permission requests show their turn scope and never grant session-wide access. Requests the agent no longer waits for expire, including after a server restart. Codex's mode selects its approval policy (`untrusted`, `on-request` or `never`) with its sandbox: `never` runs with full access, the others write only in the task folder and Pnyx's home. `bypassPermissions` is `never`, so nothing asks.
- **Paseo:** with [Paseo](https://paseo.sh) running, `--via paseo [--rule <name>] [--harness claude|codex] [--account <name>] [--prompt "..."] --folder <path>` asks the local daemon (`PNYX_PASEO_URL`, default `ws://127.0.0.1:6767/ws`) to start a Claude Code or Codex agent; the conversation and replies then go through Paseo, and the agent stays in Paseo too.
Pnyx says so when Paseo is not running and never starts it. `task paseo` checks the daemon.
- **Firstmate:** on a Hydra run by a Firstmate home (the default route there), `--via firstmate [--prompt "..."]` puts a worker request in Hydra's chat and hands it to Firstmate as an inbox note.
Firstmate dispatches the worker; its mirrored task can be nested under the Hydra task.
- **Your own command:** `pnyx-axi hydra set --hydra <id> --command '<shell command>'` sets a command, run in the task's folder with `PNYX_HOME`, `PNYX_HYDRA`, `PNYX_TASK`, `PNYX_ROLE` (`worker` or `hydra`), `PNYX_TASK_TITLE`, `PNYX_PROMPT`, `PNYX_HARNESS` and `PNYX_FOLDER` in its environment.
The session it starts attaches to its task, or becomes Hydra, when its hooks first report.

Every agent Pnyx starts carries `PNYX_HOME` and `PNYX_HYDRA`, so its hooks report to the Hydra that started it, even from a separate Pnyx home, once `pnyx-axi setup hooks` has installed this version's hook. `pnyx-axi integrations` shows which of global skills, hooks, Paseo, Firstmate, the configured command and GitHub are ready, with the command that sets each up.

Hosted agents receive only images attached to the message being delivered. If an attached file is missing or its bytes change before delivery, the turn reports an image error so you can attach it again.

Hosted Hydra context includes at most 3,000 estimated tokens of owner preferences and learnings, keeping complete lines and pointing to `owner memory list` for omitted text. A resumed native session receives only changed digest sections; owner memory returns when it changes or after compaction. Digest checkpoints are recovered from the native transcript, including after a server restart. If a checkpoint is missing or invalid, Pnyx restores the bounded full digest.

Compaction runs when requested or through the harness itself; Pnyx does not trigger it from reported context usage. Compaction restores fresh context and a recorded-history command. Native compaction keeps the event log and inscribe milestones available; it does not mark an inscribe pass complete.

Routine helpers receive their own contract, bounded owner memory, recent dialogue and the granted tasks. Claude helpers expose Bash with no skill or MCP catalog. Codex helpers disable configured MCP servers, skills, apps, plugins and web search for their thread; its native built-in tools remain available. These filters do not change worker sessions or the account's saved settings.

### Kinds, the light check and the worker contract

```sh
pnyx-axi rule init
pnyx-axi rule show
pnyx-axi rule now
pnyx-axi rule apply --file patch.json --check
pnyx-axi rule set review --when "Independent code review" --candidates '[{"harness":"codex","model":"gpt-6.1-sol","effort":"high"},{"harness":"claude","model":"claude-opus-5-5","effort":"high"}]'
pnyx-axi task start <task> --rule review
```

- **Heads dispatch:** Hydra chooses a named rule for the work; each rule has a plain-language `when` and a candidate list of harness, model and effort (plus optional mode and Fast).
`task start --rule <name>` selects within that list; without a rule it uses `default`. An explicit owner `--harness`, `--account` or `--model` wins even outside the rule, checked against that harness’s own catalog and login. Quota does not veto that choice; `--effort`, `--mode` or `--fast` alone choose nothing, so quota still picks the candidate and skips spent accounts. `--model`, `--effort`, `--mode` and `--fast on|off` replace the chosen candidate's settings for that start, from its first turn; the task records the override. `rule set <name> --when "..." --candidates '<JSON array>'` replaces a candidate list; the single-candidate flags `--harness`, `--account`, `--model`, `--effort`, `--mode` and `--fast on|off|default` edit the first candidate and keep the others. Empty model, effort and mode flags clear those settings. `rule remove <name>` removes a named rule. The `hydra` rule is Hydra's own pinned agent: every new Hydra, including one `hydra create` makes, starts on it; existing Hydras keep their own choice. Settings → Heads dispatch edits the rules and the default list in place or as JSON, with the same checks and one Apply through `rule apply`, shows which candidate of each rule would start now, and records Hydra’s direct changes in its chat. Permission increases still need the owner’s confirmation in chat.

The shipped template offers Claude and Codex in every rule: Sonnet 5.5 and gpt-6.1-sol at medium effort by default, Haiku 5.5 and gpt-6-luna at low effort for mechanical work, and Opus 5.5 and gpt-6.1-sol at high effort for well-defined implementation or xhigh for investigation. Hydra chooses the best-fitting named rule; quota-axi ranks its candidates.

Hydra changes settings directly when the owner asks or when the work calls for it, using the same checks as owner edits. This includes dispatch rules and candidates, accounts, Hydra command/session settings, project settings, Hydra defaults, helper settings and the other settings-page values. Each command that changes settings appends one short line to that Hydra’s chat.

Raising Hydra's own, a worker's or a candidate's permission level still requires the owner, including in Bypass permissions or Codex's Never ask with full access; lowering a permission level is allowed. Hydra cannot answer its own permission prompts or confirm or dismiss approval questions. Other owner-only CLI actions become saved questions with Confirm and Dismiss in chat: setup, restart, upgrade and discarding copies. A hosted Hydra in Bypass permissions or Codex's Never ask runs those other actions on its own Hydra at once. Only owner confirmation executes a stored command; repeated clicks never run it twice, and changed targets require a new question.

Heads dispatch is one document every Hydra shares: `rules`, the `default` list, `accounts`, the `main` account and the `workers` and `projects` account orders. Every section but `main` is required; `rules`, `accounts`, `workers` and `projects` may be empty objects. `rule show` prints it with its revision and every problem it has, and `rule schema` lists every field, each harness's effort and permission values, and an example. `rule apply --file <path|->` (or `--json '<envelope>'`, as Settings sends it) takes `{"version":1,"expected":{"revision":<n>},"patch":{...}}`, where `patch` is a JSON Merge Patch (RFC 7386): it names only what changes, `null` removes a key and a list replaces the whole list. Pnyx checks the whole result and saves all of it or nothing, refusing any error the patch adds; an error the saved document already had, such as an effort an older Pnyx accepted or a rule name merged from an old Hydra file, can stay until a later patch fixes it. While the saved document has an error that stops reads, starts and `rule list` fail with that error and point at `rule apply`, which still takes the patch that fixes it. The checker lists every problem at once, each at its path in the resulting document: unknown fields, names, a missing `when`, a rule with no candidates, a missing or empty `default` list, a missing `rules`, `accounts`, `workers` or `projects` object, an effort or permission mode the harness does not take, and an account an order or `main` names that is not registered for that provider or is listed twice. With no registered accounts, only the harnesses' own logins `claude:default` and `codex:default` may be named, each for its own provider. Warnings never block: a model no login's catalog lists, a rule with no candidate a worker account can start, and a missing login folder. `--check` previews the changes and remaining issues without saving, `--if-revision` or `expected.revision` refuses a stale base with `REVISION_CONFLICT`, and a repeated `--event-id` returns the first receipt without applying again, also when that first attempt changed nothing. `rule set`, `rule remove`, `rule accounts`, `account set` and `account remove` are shortcuts for one patch through the same checks.

For a candidate permission increase, Hydra proposes the change with `rule apply --propose` or `rule propose set`, using the same arguments as the direct commands. Each proposal records the values it changes, so waiting proposals that affect different values can be confirmed independently. Pending changes survive restart and appear in Hydra’s chat with their changes. Only the owner can apply one with Confirm (or `rule confirm <token> --confirm <token>`). Dismiss leaves config unchanged. If a value the proposal changes has changed since, or its result no longer passes validation (for example because an account it names was removed), the proposal shows as out of date with the reason and can only be dismissed.

Heads dispatch is saved in `~/.pnyx/config/dispatch-changes.jsonl` (`$PNYX_HOME/config/` when set). Each saved change appends one line carrying the whole resulting document with its actor, reason, changes and receipt, and the last such line is the heads dispatch every reader uses. A save is complete once its line is written: a save cut short, or one whose line could not be written, leaves the document before it. `hydra-heads-dispatch.json` and the account registry `hydra-accounts.json` beside it mirror that document for reading; a read rewrites them from the log when they differ, so change them only through `rule apply` and its shortcuts. Each line that changed the document counts toward the revision `rule show` reports. Until the first save, Pnyx reads the two files, and missing or empty `rules` and `default` use the template's; the first save writes them into the document, which is read exactly as saved from then on, so removing every rule leaves none. Account records live under `accounts` and contain only `provider` (`claude` or `codex`) and `folder` (an absolute login folder or `~/...`). Pnyx never stores tokens. The repository ships only templates, `setup/config/hydra-heads-dispatch.example.json` and `setup/config/hydra-accounts.example.json`, with one Claude and one Codex login and example rules. `rule init` saves them as the first change, keeping either file that already exists and never replacing a saved document, and takes each account's login folder from `CLAUDE_CONFIG_DIR` or `CODEX_HOME` when the command's environment sets it; change that copy with `rule apply` to list your actual accounts and rules before starting work. Until the change log holds a saved document, `rule list` suggests running `rule init`, and Hydra runs it itself when its digest lists the missing config under Setup needed; until accounts are registered, Hydra and workers use each harness's own login, named `claude:default` and `codex:default`. Everything personal (accounts, rules, preferences, memory and project profiles) lives only in the Pnyx home and is never committed. `account set <name> --provider claude|codex --folder <path> [--label <display name>]` and `account remove <name>` edit the registry; removing an account also takes it out of every account order, and the main account cannot be removed until `main` names another account. To remove the last account, set `main` and the orders to `claude:default` or `codex:default` in the same patch.

The dispatch file's `main` names the account Hydra runs on. Its `workers` maps each provider to an ordered list: for example `{"claude":["claude:work","claude:personal"]}` spends the worker account before falling back to the main one. `projects` optionally maps absolute project paths to provider account orders; a nonempty provider order there replaces that provider's worker order for tasks assigned to the project. Use `rule accounts --main claude:personal --provider claude --order claude:work,claude:personal`; add `--project <absolute path>` to set a project override. For rule dispatch, an account must be registered and listed for that provider. An explicit owner start can use a registered account or the harness’s default login when no worker order exists, and skips proven signed-out logins while preserving the chosen harness and model. For rule dispatch, a signed-out account stops the start and reports the account to sign in; only a spent account falls through to the next listed account. Hosted Claude workers receive the selected `CLAUDE_CONFIG_DIR`, hosted Codex workers receive `CODEX_HOME`, and the same login folder is kept when their sessions resume.

Register a named account inline in Settings → Accounts: choose a provider, give it a display name and point it at an existing home, a Claude Code `CLAUDE_CONFIG_DIR` or a Codex `CODEX_HOME`. `account set claude:work --provider claude --folder ~/.claude-work --label Work` does the same from the CLI. Pnyx stores the home and the label, never credentials, and does not sign in for you. Registering the first account also registers `claude:default` and `codex:default` for the logins found on this machine, so main and the worker orders that name them keep working.

The composer picker opens Provider → Account → Model. Its model list comes from the chosen account’s home, and its trigger shows the model above the account. Pinning a model saves that provider, account and model as the default for new Hydra sessions only. The same picker sets Hydra’s defaults in Settings, each heads dispatch candidate row and Add candidate. A candidate’s `account`, or `task start --account <name>`, runs on exactly that account and never falls back to another login. Each provider and account pair appears once per rule, whatever the model or controls: a change that adds a duplicate is refused, and an existing duplicate stays visible so it can be removed.

Pnyx reads each account with `quota-axi --no-credential-refresh`, adding `--profile-only` when the account names a login folder other than the harness's default, so only that folder is read; a default login is read the way its harness reads it, and joins its model evidence through `quota-axi models`. It skips models the harness's catalog does not list and candidates exhausted now. A candidate is bounded by the lowest `effective.selection.spendPriority` of its account and model windows; candidates with a known value rank highest first, and unknown quota ranks below every known one. On a tie, or when every usable candidate's quota is unknown, the first listed starts, so list order is the rule's preference; the task records the tie or the unknown quota. Stale readings are treated as unknown. Pnyx-hosted starts check models against the Claude Code and Codex catalogs the Hydra's server reads; for Paseo, its offered models are checked before selection. The chosen rule, model, account and quota evidence appear on the task. If every candidate is spent or unavailable, the start stops: Hydra must tell the owner, and Pnyx never switches to a weaker rule or an unlisted account. `rule now` makes the same choice for every rule without starting anything and prints the candidate that would start and why; `--json '<document>'` asks it of a document that is not saved yet. Each login's reading is kept for a minute.

The first read after upgrading merges each Hydra's own `heads-dispatch.json` and `accounts.json`, and an older Hydra's agent kinds, into the shared document once, as its first saved change: where two Hydras set the same value the newest file wins, and the shared `hydra` rule wins over any Hydra's copy. The shared files are kept beside them as `.before-merge` and each Hydra's files as `.merged`; the event log is unchanged. The old kind commands and `--kind` start flag are removed. Legacy quota buckets no longer choose models implicitly; list the allowed models explicitly in each rule. An existing `hydra start --via paseo` uses the configured main account.
- **Direct conversations:** owner messages sent through CLI task replies are recorded with their send receipts.
The light check also archives native transcript messages and completed Paseo replies into the same event log, including chats retained after detach and messages from an earlier task attachment. It returns a compact `conversations` digest grouped by task; Hydra treats the owner’s direct words as instructions and decides whether to act or take note. Excerpts point back to full task history, and the `through` cursor pages every event without dropping the rest. Echoes of Hydra sends and Hydra’s own answers are excluded from the digest. Unavailable native sources are reported for a later retry. Workers can escalate directly with `hydra send --task <task> --text "<question and context>"`.
- **Light check:** `hydra check` also returns an `agents` list with each attachment’s session, harness, launch route, folder, start time, last observation and current presence.
A terminal observed before this boot or a process that exited is `gone`; a daemon or process that cannot be queried is `unknown`. These are observations for Hydra to inspect with `task history` and `task show --full`; Pnyx never relaunches agents. `hydra check` prints only what Hydra tracks (messages, task creation, brief and visibility changes, declarations, open agent questions, attachments, column changes, manual moves and links) after `--after`, with each event's id, task and message action, and skips Hydra's own writes (actor `hydra`, from `PNYX_ACTOR` or `--actor`). With `--wait` it blocks until one appears, so a background command or monitor wakes Hydra only when something changed, without loading the Hydra. A Hydra that Pnyx runs is refused `--wait`, since a waiting shell call would hold the owner's messages until it returns.
- **Wakes:** when Pnyx runs Hydra, its server queues one short check turn a few seconds after something needs Hydra's judgment: a worker report or question, a `needs_you`, `blocked` or `done` declaration, a permission request, a worker turn that finished while it still declares `working` or has declared nothing, checks settling green or red on an open, ready pull request, a linked pull request merging, a worker ending with an open pull request, or a prerequisite becoming unmet or clearing.
A plain `working` or `paused` declaration that does not change prerequisite readiness and Pnyx's own moves stay on the card until Hydra's next wake; worker progress reports (`hydra send --kind progress`) wake nobody: they stay in the task's activity and join the next main wake. Each change or stall wake opens with `Why you are woken:` and one line per fact, `- [@Title](pnyx-task:<id>) <kind>: <detail>`, from a fixed list of kinds (`declared`, `asked`, `report`, `turn ended`, `checks`, `comments`, `merged`, `approved merge is green`, `quiet`, `permission`, `wait ended`, `not confirmed`, `reminder due`, `queued`, `queue released`, `kind`, `prerequisite`, `slot free`); a fact about a pull request carries its full link, and a `done` declaration while Backlog has ready cards adds `slot free` with them in order. The lines are worked out when each change lands, and a change wake ends by telling Hydra that a result always gets a reply. Every change, stall and `back after outage` wake also lists the open decisions on live tasks, oldest first: owner and worker questions, pending permissions, blocking prompts and pull requests Hydra may merge, or `Open decisions: none` when nothing waits; an item leaves the list once nothing waits on it any more. Nothing a worker sends interrupts Hydra: what arrives while it works waits, then reaches it as one turn holding each report and, when other changes came in too, a `hydra check` from the last wake, so Hydra answers a burst once. A wake counts as handled when Hydra's turn finishes, so a turn that fails offers the same updates again once Hydra runs. Your own messages never wait: one sent while Hydra works joins the running turn. Above the composer, the running line counts update records as “Reading N updates”, adding “across M tasks” when several tasks contributed. Hover or focus the count to see each task title and update kind, including waiting updates; it clears when the turn ends. Hydra's own writes (its session runs with `PNYX_ACTOR=hydra`) wake it only when prerequisite readiness changes, a busy or interrupted Hydra is not woken, and changes and reports made while the server was stopped wake it once it is back. A worker turn cut short by a server restart continues once by itself, and a hosted Hydra turn cut short resumes once: Hydra rereads unanswered messages and the changes it was checking. If that recovery turn is interrupted or fails, Hydra waits for your next message.
- **Routine helper:** each hosted Hydra has its own background helper conversation.
Fixed rules send routine worker reports and results, worker questions, blocked, `needs_you` or `done` declarations, supplied check and comment updates, plain tool permission requests, turn ends and stuck-worker nudges to it. Owner decisions, merges, dispatch and prerequisite changes, timed reviews, unknown task context and permission questions or forms stay with main; progress reports wake nobody. A task waiting on the owner (an open owner question, a pending permission, a blocking prompt or an approved merge) lets the helper classify routine updates with a narrower action grant: it may only nudge or resume the worker and answer tool permission requests that ask no question; routing, stall alarms and the helper's commands enforce the same rule. Held and automatic tasks stay on main. The helper takes its tasks whatever main is doing, except tasks main has other updates for or is handling in its running turn, including tasks whose helper outcomes or hand-backs main has not yet acknowledged. A batch holds at most three tasks and about 24,000 characters of wake text, oldest worker questions first; an update past either cap, even one on a task already in the batch, waits for the next batch. Main's wakes carry only main's updates, so helper work never rides along with them, and pending helper outcomes reach an idle main even while routine work is still queued for the helper. Overflow still queued for the helper goes to main's next wake once the helper can no longer take it: the helper is turned off or has a failed batch waiting, or the task has become main's. A helper prompt lists the open decisions of its batch's tasks, the questions it was given first and at most ten lines, then counts the rest; main's wakes still list them all. Each helper batch gets one turn bounded to two minutes, the shared Hydra contract beneath its own actor instructions, recent owner conversation, and task leases that exclude main from acting on those tasks. Main sees the active grants and their start times in its digest and inputs; reports held by an active batch stay out of main’s report envelopes. The helper keeps its supplied `helper:<batch>` actor and omits `--actor`. It resumes interrupted hosted workers with `reply` and uses `task continue` only for eligible ended outside sessions. It may answer workers’ in-scope questions and tool permission requests; a permission request that asks a question, creating work, holds, changing settings, merging and answering owner decisions remain main-only. Its conversation starts fresh after 20 turns or 100,000 context tokens; each prompt carries its last three outcomes on each granted task. A task lease held briefly by a main command is retried rather than failing the batch. Both harnesses receive an output schema; each task summary must be one nonempty line of at most 280 characters and 40 words. Supplied links are copied exactly, missing links are omitted, and Pnyx adds task references. `handled` outcomes appear directly in chat as short automated bullets, with their task references. The completion and chat message share one durable transaction: replay restores the same message, and an unchanged result on a task is not posted again. `still_waiting` outcomes stay quiet. Only `needs_main` outcomes reach main, for a new decision, changed scope, uncertainty or a consequential failure; they remain pending until main finishes its turn. Older recorded owner outcomes still reach main. A failed or interrupted helper hands its tasks back to main without retrying: main's next turn gets one notice naming every handed-back task and error, followed by the wakes the helper was given, and routine work goes to main until that turn finishes. Owner messages always go to main and never queue behind the helper. The default helper is Sonnet beside Claude and gpt-6-luna beside Codex. Configure it for every Hydra with `hydra set --helper claude|codex --helper-model <id> [--helper-account <name>] [--helper-effort <value>] [--helper-fast on|off]`, restore the default with `--helper auto`, or use `--helper off` to route every wake to main. Its provider, account, model and effort are its own, separate from Hydra’s and the workers’. Its Fast toggle is off by default and shown only for a model with Fast; Fast in a Hydra’s composer also puts every worker and helper run that Hydra starts on Fast where the model has it. Each batch records its account and home, so recovery uses them even after the setting changes. A Keychain-only Claude login may have no per-home quota reading; it then shows quota unavailable, never zero or another account’s quota.
- **Timed review:** every 30 minutes, Pnyx checks live work and wakes Hydra only for a new actionable condition since the last review. An unchanged condition stays quiet across restarts; a condition that clears and returns can wake it again.
It lists live task facts and ages, ready Backlog cards in order and available capacity, then flags approved green merges, reported external PR blockers, old owner questions, missing workers, unwatched pull requests, unmet prerequisites with assigned workers and a memory cursor behind the log. Memory lag alone never wakes Hydra. The reminder sweep posts overdue owner questions, including merge choices, directly in chat at most once every four hours, even while Hydra works, without waking it. Their clocks are saved with the grouped message. Pnyx has no configured worker limit. Reviews wait for Hydra's turn to finish and record only their own conditions, including quiet reviews. Set the cadence for every Hydra with `pnyx-axi hydra set --review-minutes <n>`; 0 turns it off. A task finishing, detaching its worker or merging also wakes Hydra with ready Backlog work.

Hydra receives a bounded “Since your last turn” block on its next ordinary turn for context only. It records dependency resumes, owner answers to task questions (including the answer), and routine helper outcomes that need no main action. `still_waiting` helper outcomes add no notes. Each note is one line, at most 400 characters; the queue retains only the newest routine note per task, up to 20 tasks, and keeps every pending owner answer. Each turn receives at most eight lines, including an overflow count and a history command when more notes remain. Only the notes shown are consumed; the rest wait for a later turn. Injected context stays out of chat, history, message lookup and Oracle results. Notes never wake Hydra, do not join an already running turn, and are removed after a successful turn consumes them. Escalations and failed helper batches keep their existing main-turn routing.

- **Stalls:** they make no event, so the server polls for them and wakes Hydra: a permission request pending 4 minutes, a working worker silent for 4 minutes or idle while still declaring working, one inside a single tool call for an hour, a paused worker whose timed wait ended (its `--until`, or 4 hours; explicit dependency waits are checked by the server instead; a `--hold` the owner or Hydra asked for never ends on a timer), and a reply its worker's session never showed after two resends.
An idle or paused worker waiting on an existing owner question stays quiet; a generic pause expiry does not nudge it or wake main. Normal supervision resumes when the question clears, while owner reminders keep their own schedule. A stall still there after Hydra's turn comes back, each time after twice the last gap, up to an hour.
- **Hydra's health:** when Hydra's session cannot start (a harness login, settings, or a resume that times out), Pnyx records Hydra as down, posts a line in the chat, and tries again after 1, 2, 5 and 10 minutes and then every 10, also after a server restart; each of your messages and each worker wake tries too, and each message of yours that fails says so.
When a start works, Pnyx records Hydra as up and posts "Hydra is back after N min". Hydra's first turn back includes the full text of your messages that no turn of its took, preserving line breaks, and worker reports from the outage follow in its next wake. A Hydra held by an outside agent is not Pnyx's to start, so its refusal is posted once and never retried.
- **Workers:** a worker follows the `pnyx-report-progress` skill and reports with `task status <task> working|needs_you|paused|blocked|done --note <text>`; silence, idling and exit change nothing.
Run `pnyx-axi setup skills` once to make the worker and CLI skills available globally in any project or copy.
- **Questions:** `task ask <task> --question <text> [--context <text>] [--choice "<label>[: <description>]"]... [--recommend <n>] [--details <text> | --details-file <path>]` records a structured question on the task.
A worker's goes to Hydra, which hears it as the worker's report, never as your words, and either answers it with `task answer <task> <question> --choice <n> | --text <answer> --reason <why>` or hands it to you with `task escalate <task> <question> --reason <why>` under the same id. Hydra asks you directly (`--to owner`); workers cannot. Ready pull requests under owner-merge rules get shared Review, Merge and Hold controls on their linked cards. A question to you moves the task to Needs you and shows in full on its card's Context tab with its context, choices, recommendation and details; you answer with a choice, your own words or both. The answer reaches whoever asked: a worker through its session's reply route, resolved once delivered. Until then the card shows the saved answer’s delivery state instead of asking for another answer; a failed send can be sent again from the task. A send that may have landed holds the question until someone checks the session and, only if it never arrived, answers again with `--undelivered`. Hydra receives the answer as your own message naming the question. If you answer in conversation, Hydra can record your newer message with `task answer <task> <question> --from-message <id>`, saving your words and their message id. The task card shows “Recorded as your answer” with Undo answer to reopen the question; Hydra-wide questions keep these controls in chat. If the current answer is **Hold** on a merge question, Hydra may replace it with `task answer <task> <question> --from-message <id> --choice Merge` only when that saved owner message is newer than the Hold answer and actually tells it to merge that pull request. The card and history show that Hydra lifted Hold and quote your message; Undo answer restores the previous Hold. Hydra can instead ask again with `task reask <task> <question> --reason "Confirm the merge again"`: fresh Review, Merge and Hold controls appear on the card without a pop-up. Re-asking grants no merge approval; your new Merge answer approves only that question’s pull request, still subject to green checks. A conversational answer to the re-asked question must also be newer than the re-ask. For a merge question, add `--choice Merge` or `--choice Hold`; for a go question, add `--choice Go` or `--choice Hold` to record which action your message approves; Pnyx never guesses from your words. To record the answer and relay it to the worker in one call, Hydra uses `reply <task> --question <question> --from-message <owner-message> --text "<relay>"`, with the same explicit Go/Hold or Merge/Hold choice where needed. Both this call and the worker route of `task answer --from-message` save the validated owner decision and outgoing message together before delivery. The question closes once saved, including when the worker route is missing; failed, queued or unknown delivery remains a separate receipt in Updates. A failed delivery can be retried with `reply <task> --text "<relay>" --idempotency-key <reply-id>`; that key preserves the saved answer and original relay. An uncertain delivery is not resent automatically. Only after checking that it never arrived, repeat `task answer` with the same question/source, `--event-id <reply-id>` and `--undelivered` to retry its saved outgoing message. Undo answer reopens the question and prevents further retries of that decision. A plain reply is feedback, not an answer. A merge question closes when its own pull request merges or closes. Ordinary owner questions close when answered or when their work explicitly finishes or is cancelled; completing an investigation, ending a session or merging related code leaves them open. `task close-question <task> <question> --evidence <link or recorded fact> --reason <why moot>` remains available for questions linked to reports and moot worker or Go questions; a merge question requires its own recorded merged or closed link. An ordinary owner question cannot use evidence closure to bypass its answer or task lifecycle. A closure records no owner decision. A report or an unrelated message never answers a question. Task questions stay on their cards; chat shows blockers, explicitly discussed tasks and questions without a task. The Waiting on you row opens task cards or jumps to a Hydra-wide question in chat. `hydra check` and the digest list open questions, and the task's Updates keep the whole exchange. Who asked and who answered comes from the actor, as everywhere in the CLI: a session Pnyx runs writes as its own actor whatever `--actor` says, and an unlabelled `cli` counts as you.
- **Binding a session yourself:** `hydra set --session self` and `task attach <task> --session self` pick the session running in the caller's own Paseo terminal, tmux pane or Herdr pane.

## Using Pnyx

Create a task inline in any column with **+ Add task**, enter its title and initial prompt, then save. Saving opens the card without launching an agent. **+ Add column** creates a column and focuses its placeholder title. Creating a task clears active filters so the title stays visible. Use the pencil in a task’s hover toolbar to edit its title and brief (see Cards), double-click a column title to rename it, and drag cards or column headers to move them; a card dropped on another goes above or below it by where it lands. Column deletion asks for inline confirmation and offers Undo.

- **Hydras:** the left panel lists every Hydra in creation order and expands to its projects, with live workers and waiting asks per project. Drag a Hydra to move it; the order is saved with `hydra set --position`.
Click a project to filter its cards; click again to show all cards. Right-click a project for **Copy path** and, on the current Hydra, **Detach…** (tasks and history stay). Click a Hydra name to switch in place on the same server, or double-click any Hydra to edit its name and icon. Loaded Hydras keep their cards, open conversation, drafts and scroll position in the tab; a first visit keeps the current Hydra visible with a loading message until the next one is ready. Browser Back and Forward follow Hydra switches. **＋** beside Hydras adds a Hydra with a Greek name you can type over (see Create Hydra above).
- **Card states:** the status, update time and project lead each card, followed by its title.
The agent appears as its icon; hovering names it, and hovering the time shows when the task was created. A long project name shortens first in a narrow column. The badge comes from observed facts and declared waits: Waiting for you (questions and permissions), answer delivery states, On hold (owner discussion), Stopped, Running <tool>, Running background work, Working, Waiting for Hydra, Checks failed, Waiting for CI, Waiting for <prerequisite>, `Waiting: <dependency title or paused note>`, Queued or Done. Owner actions and explicit waits take precedence over active work, which takes precedence over passive checks and queues. Hover the badge for simultaneous reasons and the observation time of PR checks. Unreadable checks say Checks unknown. Idle requires a settled native turn with known-empty queued and background work; sessions without that evidence say Activity unknown or No worker assigned. Worker declarations remain notes in Current state and Updates and still control scheduling and column placement. A current paused note also supplies the wait badge; a newer worker turn, question for Hydra or owner answer makes it stale. The Oracle also finds a task by the observed badge's words. A gold question box opens its answer controls or prepares a reply in Hydra’s chat. Links use GitHub, Linear or paperclip chips, with overflow behind +N. Link tooltips wait 1.5 seconds and show the full title and URL above the chip. Tooltips hide the top-edge action pill without changing card height. Stopped workers show a red square and their stop time; ask Hydra in chat to continue them. A copy that needs attention says “copy not cleaned”. The column ⋯ menu includes Copy ID. Newly created cards and columns use a kind and a random UUID; existing IDs remain valid.
- **Columns:** every Hydra starts with Queued (Backlog), In progress, Needs you, Parked and Done.
Code computes the card's facts and places it in the first column whose rule matches, with no model involved. Queued holds unfinished unassigned, queued-behind and discussion-held work; held cards show On hold. In progress holds working workers, waits on checks or Hydra, and worker blockers. Needs you means an open owner question, permission, merge or go decision, or a due reminder. Parked holds paused or ended workers with unfinished work. Checked done declarations and all non-abandoned linked pull requests merging place work in Done, even with a discussion hold. The hold remains and applies again if the task reopens. Successful starts and queue handoffs declare working at once; delivered answers restore the appropriate phase. A finished turn or successful worker session never completes a task. Migration adds missing rules and upgrades unchanged default rules, preserving custom rules, names and order. A default-rule upgrade moves only visible tasks still in their previous automatic destination; manual placements stay put. Older layouts still place cards whose column disappears by status. A manual move, including into a custom column, lasts until a phase change selects a different rule destination; repeated notes and unrelated edits leave it alone. When you ask Hydra to change a column, it updates its rule; manual moves remain available for exceptions. Firstmate-linked Hydras keep Firstmate's placement.
- **Firstmate Hydras:** the five default columns are always present.
You can rename, describe and reorder them and add your own, but deleting one is refused in place with “Can't delete: this column is tied to Firstmate's records”. Cards move between them by each column's role, whatever its title, from Firstmate's records, with Firstmate's latest status line as the reason: a queued item goes to Queued, work in flight to In progress, an open decision, a failed or blocked latest line or a captain hold waiting on you to Needs you, a dated, aged, blocked or other hold to Parked, and a closed item to Done. A card you drag into a column of your own stays there until its Firstmate record changes.
- **Task updates:** card height is bounded by its visible content minimum and full content maximum, and an open card starts near half its column.
Drag a card's bottom edge to set its height, closed or open; each card keeps both heights, and a card taller than its column scrolls with it. At rest a card shows its open question and its Current state, the worker's newest status note or progress report. An open card has two tabs. Context holds the open questions in full (context, details and choices, answerable with a choice, your own words or both), the Intent Hydra wrote when it created the task, the Current state with its source and age, and the labels, links and reminder; it scrolls inside the card so the status, title and tabs stay in view, and with questions open a row above them jumps to Intent and Current state. Activity holds your words on the task, Hydra's instructions to the worker (Space or a click on the title shows them), the investigation report and the Updates, newest or oldest first: what you asked about the task (your messages to it and Hydra chat messages that tag it), Hydra's paragraphs about it (when a hosted Hydra's chat reply has a paragraph or list item that starts with the task's reference, Pnyx copies it, redacted, and your chat message that turn answered onto the task as the turn ends), its messages to the worker, decisions, worker declarations, moves with Hydra's reason, renames, worker start, links attached and merged, briefs, outcomes and Done. Each row starts with an icon that names who or what it is. Decisions answered together appear as one numbered block with the question, answer, who decided and why. Entries that belong together fold only when there are two or more: entries of one moment become one row, your message and Hydra's reply become one exchange, and runs of worker declarations or card changes become one closed row. Long text stops at three lines with Show more. Hovering a row that can open tints it, and a click anywhere in it opens or closes it without closing the card; selecting text does neither. Worker attach and detach, project changes, reminder changes, automatic hides, hook refreshes, copies, transcript summaries and ordinary delivery receipts stay in recorded history. A move reason that repeats the previous update is left out, and a Firstmate task shows its captain's intent, its decisions and the pull request named at the end of its backlog title. Worker declarations stay on the card. Worker reports have their own closed Reported to Hydra row. Hydra’s chat shows your messages and its final replies; earlier progress notes, tool calls and thinking fold with the turn’s changes, and Focus mode hides the tool calls and thinking. A finished turn never marks a task Done.
- **Tasks and agents:** Hydra attaches or reassigns an agent; the server also follows a saved worker queue after work lands.
CLI start and resume requests go to Hydra; Firstmate-linked Hydras send them to Firstmate’s inbox. The existing attachment stays until Hydra changes it. Hydra and scripts can use `task create --title "Work to do" --brief "Initial prompt"`, `task sessions`, `task attach <task> --session <session>` and `task detach <task>`. Attaching or detaching never starts or stops a process. Hydra can continue an ended outside Claude Code or Codex session with `task continue <task>` after checking its recorded process has exited; `task continue <task> --check` only reads eligibility. A fresh start uses `task start <task> --via pnyx --replace-session <session> --folder <path>` and preserves the attachment when validation fails.
- **Task delivery:** a CLI task message is saved in Hydra’s durable queue with its task reference and sent through the attached worker’s route.
Without an agent, it addresses Hydra and stays in task history for assignment. Agent delivery and Hydra queue acceptance have separate receipts; Firstmate Hydras also report the inbox delivery. Queued means available for Hydra to read, not handled. Failed or uncertain routes keep the saved task message. Retrying the same attempt never resends a confirmed or uncertain worker delivery, and never duplicates the Hydra message. The CLI equivalent is `pnyx-axi reply <task> --text "Context" --task-message --idempotency-key <key>`. Ordinary `reply` remains a direct worker send.

- **Agent questions:** when a session in a tmux pane waits on its own question, permission, plan or MCP form prompt, the open task (or Hydra's chat, for Hydra's session) shows it with the options its terminal shows; answering types the keys that prompt expects.
It shows as answered until the session's hooks report it moved on. Other terminals are answered in the session itself.
- **Hydra:** its chat stays docked on the left, with its composer at the bottom.
Enter sends and Shift+Enter adds a line. Mod+B hides the left panel completely and brings it back. Create Hydra (the **+** beside Hydras) adds a Hydra at once with an unused Greek name and its icon, opens it, and puts its name in the left panel into edit: type to replace it, Enter or a click away saves, Esc keeps the name it has. Every Hydra has a Greek name and icon: `hydra create` without `--name` picks one, and the server names any Hydra still called by its id (such as `default`) once at start; a Firstmate Hydra keeps its home's name. Names show bold with their icon. Click the name in the header, double-click a Hydra in the panel, or right-click it and choose **Edit** to change the name and the icon together; clicking the header's icon changes just the icon. A name is at most 40 characters and unique among your Hydras; Esc puts back the saved name and icon, and a rename never changes the icon. The header says Down since a time and retrying while Hydra cannot start (the offline badge is the browser's own connection). In the left panel, a dot beside each Hydra turns into a blue ring while its agent runs a turn. A sent message shows each image as the same compact card, in the place it was written; click one to open it. The Comments card above the draft and attached file cards share that card's size. Its agent-and-model, effort, permission mode and Fast pickers save choices for the next message. The first picker lists Claude Code's and Codex's models under their names and shows the chosen model with its agent's mark; choosing another agent's model switches both. Each effort level shows its own figure, stronger from low to max, and each permission mode an icon for what it lets the agent do on its own; Mod+click or holding an option picks it and pins it Pnyx-wide: every new Hydra starts with it, while each existing Hydra keeps its own choice. Fast mode is a lightning toggle, gold when on, and every Hydra starts with it off. When the composer is too narrow for these pickers side by side, they fold into one button showing the model and effort; it opens Settings, which lists Model, Effort, Mode and Fast with their values. Model, Effort and Mode each open their own list with a back arrow, and Fast turns on or off in place. The pickers come back once the row has room. Hydras, the default columns, the Oracle and the composer's attach, send, effort and skills controls draw game-icons.net identity icons; every other icon is Tabler. A ring beside Send fills with how much of the context window Hydra's session uses, and shows a dashed outline until the session reports it; hovering it shows the tokens and session cost the session reported, and the account's plan windows with their resets: those the agent reported itself until they reset (Claude Code with each request, Codex's app-server for its account), the rest from a cached quota-axi read. The usage view also shows recorded helper batches, input tokens and cost separately, plus combined cost when both figures are known. Helper usage survives restart; unmeasured batches are identified. Combined cost adds the current Hydra session to recorded helper batches, so it is not an invoice or a comparison over matching periods. Current context, recorded task totals and plan windows are separate data. The shared panel shows unknown context once as “Usage unavailable”; only reported context is shown. A transcript-only Claude session shows its used tokens without an unreported capacity or cost. `pnyx-axi hydra usage` prints current context, recorded totals and plan windows once; `--task <id>` reads a task session. `hydra usage refresh` refreshes plan limits, and `--force` bypasses the quota cache. Model, effort and permissions always name a value: Hydra's own choice, else the `hydra` heads-dispatch rule's, else what the harness runs by default, which is then saved. A new permission mode reaches a Claude Code turn already running; Codex takes it on its next turn. The first message starts Hydra’s own Claude Code or Codex session in its agent folder with the pnyx-orchestrate skill; replies stream into chat and later messages resume it, including after a server restart. A message shows in the chat the moment you send it, faded until the server records it, and the composer clears at once; a message the server refuses stays in the chat marked Not sent, and Retry sends that same message again without making a copy. While Hydra works on a turn, three dots and the time the turn has run sit just above the composer, from the send until the turn ends, and a **Stop** button next to Send ends that turn (`pnyx-axi hydra stop`); its workers keep going. The chat stays on the newest message while it grows; scrolled up, it stays put and a chevron above the composer jumps back down. Each finished turn ends with a quiet footer: earlier turns say how long they worked, the latest says when it stopped (hover for the other), with a button that copies Hydra's reply. Your messages always show when you sent them and a copy button. Login and turn errors show in red where Hydra's reply would be; a start that fails shows as a line from Pnyx. A Firstmate-linked Hydra has no picker for Hydra itself because Firstmate owns its agent. Reminders and History have no separate web views; the card’s Remind action still schedules reminders, and the CLI exposes waiting reminders and recorded history.
- **Columns:** drag a header to reorder columns, or focus a header and use Mod+Left/Right.
The ＋ creates a task at the top. The ⋯ menu copies its ID, renames, edits the hover description or deletes the column with an inline Yes/No confirmation; on a Firstmate Hydra, Delete on a default column shows why it is refused instead. Drag the always-visible handle at the right edge of a column or Hydra to resize it; Settings resets widths to their defaults. Sizes, moves, renames and preferences update locally while saves run in the background. A failed save restores the saved value and shows an error.
- **Cards:** click anywhere on a card outside its title, or press Enter on its focused title, to open or close it at the same width.
One card per column can stay open. A working card shows three moving dots for the whole turn. Click a title, or press Space on it, to show Hydra's instructions to the worker in the Activity tab (“No brief yet” when it has none); a second click or Space folds them, and they start folded when the page loads. The hover pill offers Edit title and brief, Remind and Hide. Click the pencil, or press Mod+E or F2 on a focused title, to open the task with its title and brief in one editor: Enter in the title moves to the brief, Mod+Enter or Save saves both, and Escape or Cancel discards them. An empty title keeps the last saved one. The edit shows at once; a refused save restores the old text, shows the reason and reopens the editor with your drafts. Saving never messages a running worker; ask Hydra when it should pick up the change. Ask Hydra in chat to reassign work or create a subtask, or use the CLI. Summary and decision notes stay in the task record for Hydra.
- **Conversations:** replies use Markdown, user messages appear on the right, and thinking, when shown, uses one-line rows. In Hydra's chat, tool calls and thinking stay inside the collapsed progress above a reply, or below the latest message while a turn runs, each with a plain label such as Reading release.txt; open a row to see the command and its output.

## Retention and appearance

Settings apply to every Hydra. The theme, text sizes, cards and chat switches, keyboard bindings, default column and Hydra chat widths, Hide Done, the review cadence, the routine helper, whether the Oracle keeps its last filters (`oracleRememberFilters`), the Hydra list's order as Hydra ids (`hydraOrder`) and the diagnostic logs (`logs`: `off`, `on` or `detailed`; `logDays`, the days kept, 1 to 365; `logMaxMB`, their total size cap in MB, 1 to 100000) live in one append-only log, `~/.pnyx/settings/events.jsonl`, which every Hydra reads and the server pushes to open pages. `pnyx-axi settings show|schema|set --json '<patch>'` reads and changes them. `view set --hydra <id>` saves those shared keys there; width settings also resize the named Hydra, replacing its relevant dragged and per-column overrides. `settings set` changes only the shared settings and leaves every Hydra’s own widths intact. A repeated `--event-id` saves once, including a save that changed nothing, so a retry never undoes a later edit. The first read moves each old value from the Hydra that changed it last, counting an old reset to the default as a change. `layout reset --all` resets dragged widths in every Hydra. `defaultColumnWidth` supplies the width of existing and future columns without a per-column override in `defaultColumnWidths`; dragged widths stay local until reset or a width change through Settings or `view set`. ## Restart

The server runs every agent Pnyx starts as its own child process, and `stop`, `restart` and upgrades stop them with it. When the server starts again, a turn it cut resumes from the agent's saved Claude Code or Codex session, up to three restarts in a row; an idle agent resumes with its next message. A pending permission request expires and the resumed agent asks again. A direct message the server had handed to an agent without its confirmation shows as possibly not arrived; Pnyx never sends it again by itself, and sending it again sends a new copy. A server that died without stopping its agents leaves their process ids in each Hydra's `children.json`, and the next start stops the ones still running before it resumes any session.

`pnyx-axi` is a client of the server: every command except `serve`, `stop`, `restart`, `setup`, `upgrade` and help runs in the server, which answers with exactly what the command prints. A command that finds the server down starts it through its login service; with none installed, it says Pnyx is not running. `pnyx-axi context`, which the session-start hook runs, never starts it and prints nothing while it is down.

Use `pnyx-axi restart` or `/restart` in Hydra chat to restart the server without upgrading or calling an agent. It starts a stopped server, stops a stuck one only after verifying its process identity, and confirms the replacement is ready.

While a restart, an upgrade or Hydra's own compaction stops Hydra, everything sent to it (owner messages, worker replies, helper results and wakes) waits in its one queue and shows in the queue box. When the stop ends, the chat shows one divider (Restarted, Upgraded, Compacted, or the failure), and Hydra's next turn is one recap of what waited, with the owner's messages in full; back-to-back stops recap once, after the last. A clean stop that nothing waited on starts no turn.

## Discovery and bounded receipts

Run `pnyx-axi` for live state, `--help` for command groups, and a command with `--help` for its syntax. Output hints describe relevant next steps; they grant no authority. Routine output stays compact. `task show` shows the newest five owner asks and up to five questions, unresolved first, with total and open counts; `task show --full` explicitly retrieves the complete record.

`apply` receipts preserve operation/event IDs, aliases and revisions. The default diff names changed fields, clips long text and reports collection counts instead of embedding whole histories. `apply --check --full` opts into complete before/after records without writing. For durable details after a write, use `task history <id> --full`; keep the same event ID and document on retries.

Lifecycle declarations and reports serve different purposes. `task status working` and `paused` record state without waking Hydra. Routine `hydra send --task <id> --kind progress --text "..."` waits for its next wake. A ready trial, findings or other actionable result uses `hydra send --task <id> --text "<result with links>"` without `--kind progress`, before pausing. Questions use `task ask`; blockers use `task status blocked`. Recorded, queued and host receipts do not confirm the owner has seen a result; Hydra relays it.

### Reading history for inscribe and compaction

`pnyx-axi hydra history --since last-compaction` reads the recorded conversation since the last successful compaction; `--since last-inscribe` starts after the last successful inscribe, falling back to the last successful compaction when no inscribe milestone exists. An explicit successful milestone ID pins the same boundary, and `origin` reads from the beginning. Owner messages, assistant replies reconstructed from transport chunks, task briefs, intents, the owner's words on tasks and helper results share one rendering and token estimate. Helper summaries retain their task and outcome status; unchanged waits are omitted. Automated chat copies of helper results are not repeated.

Pages default to 6,000 estimated tokens (`--budget <tokens>`). A page always ends at a whole message; an oversized first message is returned whole. Normal pages stay below about 25 KB of command output, including escaping. Run the suggested command with `--after <cursor>` while `more` is true; next-page help preserves a custom budget. Each cursor pins the boundary and the upper log position, so later arrivals are left for a later pass. `--count` prints only the count for that same rendered history.

`hydra inscribe start` returns the milestone ID, snapshot and history command. After every page is read and memory is saved, run `hydra inscribe finish --key <id> --through <snapshot>`. Use `hydra inscribe fail --key <id> --error "<why>"` if the pass fails. Only a finished milestone advances the boundary; no separate memory cursor is needed. Commands use `--hydra <id>` when the target Hydra is not already in the environment.

## Debugging a Hydra

`pnyx-axi debug timeline --hydra <id>` pages through event identities and the warnings and errors in the diagnostic logs. Narrow it with `--task <id|key>`, `--message <id>`, `--batch <id>`, `--session <id>`, `--since <ISO timestamp>` and `--until <ISO timestamp>`. Filters intersect and time endpoints are inclusive. Original sequence, transaction, message, native and source identifiers are preserved. Recovery records retain their actual target session and expose a different envelope session as `recordedSessionId`; timestamps order the combined view, with sequence breaking ties. Conversation and transcript bodies are omitted. The default page has 50 records, `--limit` accepts 1 through 200, and `--cursor` continues with the same filters. Service records come from the warnings and errors in the last 16 MiB of the log files, newest day first, then `service.log`, which held them before the log folder; `serviceTailTruncated` identifies this limit. A warning or error about no Hydra in particular, such as a full log folder, is in every Hydra's timeline. Legacy text lines have no guessed identity. Missing records do not establish that a send never happened.

`pnyx-axi debug performance` reads the diagnostic logs of the last hour, or of `--since` and `--until`: each action's count, typical (median) and worst duration, total time, errors and warnings, the server's memory, CPU and event-loop delay over time from its process line, and the slowest actions (10 by default, `--limit` up to 100). `--hydra <id>` keeps that Hydra's lines and the server-wide ones, and the routine helper always reads only its own Hydra's; `--operation <prefix>` keeps the operations starting with it, such as `command` or `turn.end`. Output stays bounded, so Hydra and workers can run it while diagnosing slowness. `pnyx-axi logs` shows the log folder, the logs setting, the days and size kept and each day's file, and `pnyx-axi logs clean` deletes every file now.

`pnyx-axi debug health --hydra <id>` reads unfinished helper batches, their known native session and deadline, unsettled inputs, sessions waiting for settings retirement, pending completions, the oldest eligible spool entry, and the scheduler's last successful synchronous pass. A pass can start asynchronous work that later fails. Native observations and scheduler timestamps are scoped to the running server and reset at restart. Historical batches without a current deadline or native binding report unknown. Each returned collection uses the same 50-record default and 200-record maximum. Hidden spool temporary files are excluded. Lease inspection checks holder liveness without removing files and keeps malformed or unreadable entries occupied. Queries never harvest transcripts, start workers, resend messages or release ownership.

When the routine helper is available, safe failed-message recovery uses these same health facts. It accepts only a definitively failed plain message from the last 30 minutes to an attached, idle, unleased Pnyx-owned worker. The source session and assignment generation must still match. It reuses the original idempotency key, records each attempt before sending, permits at most two attempts with a 30-second pause between failures, and records the outcome. Controls, answers, held tasks, buffered instructions, outside sessions, unsettled native work and unknown delivery are excluded. An unconfirmed attempt survives restart as unconfirmed and is not sent again. Queued receipts stay visible in health, and a later delivered receipt resolves the attempt without sending. Failure to persist a recovery record stops that incident for the running server and is exposed in health. Exhaustion or uncertainty stops recovery and adds one concise notice for the owner. A temporary lease or busy session defers another eligible attempt without a stop notice. The attempt budget survives restart; it is never reset by a diagnostic query.
